7. 控制台 "keychain-2.db" 行只看 `stat` 成功就显示权限 → 权限 600 且属主是 root 时仍显示绿色"可访问"，误导（`RootViewController.mm:114-119`）。
8. 进程页打开后工具栏不再隐藏（清理页有 `viewWillDisappear` 收尾，进程页没有）→ 返回控制台后底部留一条空工具栏（`MFProcessViewController.mm:48` vs `MFResidueViewController.mm:83-86`）。
9. `mf_redirect_klog()` 把 stdout/stderr `dup2` 到文件且**永不恢复**（`MFKernelBridge.m:194-212`）⇒ kopen 之后所有 `NSLog`/`printf` 都被吞进 `mf_kfd.log`，现场诊断困难；同时泄漏 1 个 fd。
10. 覆写 `__assert_rtn`（`MFKernelBridge.m:162-172`）：kopen 期间任何断言（不只 kfd 的）都会被 `longjmp` 劫持；`g_fail_armed` 之外退化为 `sleep(30)+exit(1)`（这是有意的，但要写进风险说明）。
11. `posix_spawn` 未设 `POSIX_SPAWN_CLOEXEC_DEFAULT`（`MFHUDLauncher.mm:57`）→ 子进程继承父进程全部 fd（包括 kfd 日志 fd）。
12. `hudPID` 只用 `kill(pid,0)` 探活（`MFHUDLauncher.mm:22-32`）→ PID 复用/僵尸进程会误判"悬浮窗正在运行"；建议再用 `proc_pidpath()` 比对自身可执行路径。
13. `startHUDWithError` 里 `usleep(400ms)` 在主线程同步执行（`MFHUDLauncher.mm:79`）→ 点按钮后 UI 卡 400ms。
14. 两角色设置不同步：`MFSettings`/`MFOffsets` 都是 per-process 单例，只有文件是共享的；HUD 进程改配置后主进程侧看到的是旧值（`MFSettings.mm:12-25`）。
15. HUD 没有任何"退出/自杀"入口（`MFMenuUI.mm` 只有"隐藏"），主进程被杀后可能留下孤儿 HUD 进程，只能靠重启或外部工具清掉（对比：原版另有 launchd 分支，【补充分析】§2）。

#### 1.4 危险操作的安全闸门够不够？——**不够，有 4 个缺口**

链路现状：扫描（dry-run）→ 默认全选 → 可取消勾选 → ActionSheet 二次确认（含"不可撤销"文案，`MFResidueViewController.mm:157-165`）→ 后台删除 → 结果弹窗。

| 缺口 | 依据 | 说明 |
|---|---|---|
| ① **没有真正的"两阶段提交"** | `MFResidueViewController.mm:99-119` → `176-201` | 清单在内存里停留任意长时间（用户可以去别处、可以锁屏）。删除时只重核了保护名单（`MFCleanup.mm:205-208`），**不重核规则命中、不重核"父目录还是不是当初那个配置目录"**。TOCTOU 场景：`/var/mobile/Library/Caches/foo` 被系统换成另一个 App 的缓存目录，仍然照删。建议删除前对每项做一次 `lstat` 并比对 `st_ino/st_dev`（把 inode 存进 `MFCleanupItem`）。 |
| ② **符号链接语义没有显式处理** | `MFCleanup.mm:181-187`、`210` | `fileExistsAtPath:` **跟随**符号链接，所以"清单里显示目录"的项可能只是个指向别处的链接；`removeItemAtPath:` 对**最后一级**符号链接只做 `unlink`（安全），但中间层级会被解析。若某配置目录的一级子项是指向 `/var/mobile/Containers/Data/...` 的链接，删掉的只是链接本身（可接受），但展示给用户的信息是错的。建议用 `lstat` 判断类型并标注"链接"。 |
| ③ **路径穿越**：不存在 | `MFCleanup.mm:158-165` | 名称来自 `contentsOfDirectoryAtPath:`（不会返回 `.`/`..`），且路径是"配置目录 + 一级子项"拼出来的，**无法构造出父目录**。`/var/mobile` 本身永远不会被当作候选项（它只能作为规则根出现）。这条是安全的【已证】。 |
| ④ **默认全选** | `MFResidueViewController.mm:107` | 对"作用于本 App 之外系统目录"的操作，默认应当是**全不选**（或只默认选中白名单外的高置信残留，如 `Sileo/Filza/Cydia/...`），并由用户显式勾选。当前"扫完就全勾上+一个大按钮"是这套闸门里最薄弱的一环。 |

- **没有"预演结果可导出/可留痕"**：删了什么只有一条 toast，`MFCleanupResult.deleted` 不落盘。建议把删除清单写进 Documents 日志（事后追责/恢复参考）。
- **备份能力缺失**：删除前不产出任何备份（目录态备份代价高，但至少应把"待删清单+大小+inode"落盘，并在设置里提供".bak 搬运"选项）。

#### 1.5 `removeItemAtPath` 对目录会递归删吗？会不会误删父目录？——**递归删；不会误删父目录**

- 递归：`NSFileManager removeItemAtPath:` 对目录是**整棵删除**（与【补充分析】§5 的表述一致："如果被选择的是目录，`removeItemAtPath:` 仍可能删除该目录及其内部内容"）。
- 父目录：不会。候选路径恒为"规则根 + 一级子项"（`MFCleanup.mm:163-165`），且 `contentsOfDirectoryAtPath:` 不返回 `.`/`..`。
- 但要注意**软删除缺失**：递归删 `/var/mobile/Library/Caches/<X>` 会把 `<X>` 整棵树删掉；对 `default=blacklist` 的目录，这会一次性清掉几十上百个第三方目录（见 §三 数据丢失标注）。

#### 1.6 有没有可能删到不该删的（例如 `/var/mobile` 本身）？——**文件系统层面不会；数据层面会**

- 结构上安全：不可能删到规则根自身（见 1.5）。
- 但**"不该删"的判定标准是配置说了算**。在目标机（TrollStore、非越狱）上，真正会被删到的是 `default=blacklist` 的 12 个目录里"非白名单成员"：
  ```
  /var/log                                   ← 系统日志目录（除 com.apple.* 等白名单）
  /var/mobile/Library/Application Support/Containers
  /var/mobile/Library/Caches                 ← 第三方 App 缓存（含 ch.xxtou.hudapp.pid 等，但有 .pid 保护）
  /var/mobile/Library/Cookies
  /var/mobile/Library/HTTPStorages
  /var/mobile/Library/Preferences            ← ★ 数据丢失主战场
  /var/mobile/Library/Saved Application State
  /var/mobile/Library/SplashBoard/Snapshots
  /var/root/Library/Caches · HTTPStorages · Preferences   （mobile 身份读不到 → 实际跳过）
  /var/tmp
  ```
- 缓解事实【已证】：配置**没有**把 `/var/mobile/Containers`（App 数据容器）纳入范围，所以不会直接删 App 沙盒数据；`/var/mobile/Library/Preferences` 白名单里有 `.GlobalPreferences.plist`、`NetworkInterfaces.plist`、`wifid.plist` 等关键项，且 `^com.apple.` + `.apple` 子串保护会挡掉全部 Apple 项。
- 未缓解：**`com.opa334.TrollStore.plist`**（以及任何 `com.opa334.*`、`com.tencent.tmgp.*` 偏好）都在删除范围内。

### ★ 二、清理 Key（keychain-2.db）

#### 2.1 SQL 是否与分析一致？——**一致【已证】**

| 项 | 分析（【清理Key】§1.2/1.3） | 复刻 | 结论 |
|---|---|---|---|
| 路径 | `/var/Keychains/keychain-2.db` | `MFPaths.mm:19` | ✅ |
| 语句 | `DELETE FROM %s WHERE agrp like '%%%@%%'` | `MFKeychain.mm:111/121`（`%@` 为表名、`%%%@%%` 为 bundleID） | ✅ 语义等价（`%bundleID%`） |
| 表 | 遍历 `genp/inet/cert/keys` | `MFKeychain.mm:16` | ✅ |
| 目标 | 4 个腾讯游戏 | `MFKeychain.mm:44-49`（与【清理Key】§3.2 的四条 CFString 长度核对吻合） | ✅ |
| dry-run | 原版无（直接删） | 复刻版加了"先统计再删"（`RootViewController.mm:363-399`） | ✅ 更稳 |

#### 2.2 SQL 注入风险：**当前 0，改成可配置后是真实风险（且不止引号一个问题）**

- 现状：4 个 bundleID 硬编码（`MFKeychain.mm:44-49`），表名来自固定数组（`MFKeychain.mm:16`），因此不可注入【已证】。
- 一旦 bundleID 变成可配置（比如让用户在 UI 输入）：
  - `'` → `sqlite3_prepare_v2` 失败 → 当前代码**只 `NSLog` 后 `continue`**（`MFKeychain.mm:86-88`）→ 静默少删（不报错）；
  - 更危险的是 **LIKE 元字符**：`%` 与 `_`。输入 `com.tencent.%` 或 `%` 会命中**远超预期**的行 → 钥匙串被大面积删除。这比引号注入更隐蔽（引号会报错，通配符不会）。
- 修法（任一）：
  ```objc
  // 1) 绑定参数 + ESCAPE，把 % _ \ 转义
  "SELECT COUNT(*) FROM %@ WHERE agrp LIKE ? ESCAPE '\\'"
  // 2) 或改用子串判定，彻底躲开通配符语义
  "SELECT COUNT(*) FROM %@ WHERE instr(agrp, ?) > 0"
  ```
  同时把表名限制在固定白名单内（已有），并给 `sqlite3_step` 的错误分支补 `res.error`。

#### 2.3 `SQLITE_OPEN_READWRITE` 能写吗？权限够吗？——**能写（语义正确），但本机权限不够**

- `SQLITE_OPEN_READWRITE`（`MFKeychain.mm:58-59`）是"读写、不创建"，语义上足够 `DELETE`【已证】。
- 三层权限门槛，任一不过就失败：
  1. 文件本身：`keychain-2.db` 实测 **0600**（用户已观测）。属主若是 `root`，mobile(501) **连读都做不到** → `sqlite3_open_v2` 直接 `SQLITE_CANTOPEN(14)`；
  2. **目录写权限**：SQLite 需要在同目录创建 journal / `-wal` / `-shm`，`/var/Keychains` 属主 root ⇒ 即便文件可写也可能失败；
  3. **并发**：securityd 长期持有该库。若库处于 WAL 或 rollback 模式且被锁住，未设置 `sqlite3_busy_timeout()` 会立刻 `SQLITE_BUSY(5)`。
- 结论（与 P0-3 同一根因）：**在目标机上，"清理 Key"必须由 uid 0 的进程执行，否则必失败**。原版的 `clkcin2:bundleID:` 由谁执行在分析里是【未证】（【补充分析】§5 只证了游戏模式走 uid-0 子进程），但以 `keychain-2.db` 的 0600 权限推断，**它也必须跑在提权进程里**。
- 真机可验证的精确预测：点"清理 Key"应看到
  `sqlite3_open 失败(rc=14): unable to open database file`（`MFKeychain.mm:62-63`）。
- 附带建议：加 `sqlite3_busy_timeout(db, 3000)`；`open` 成功后先 `PRAGMA quick_check` 或至少读一次 `SELECT count(*) FROM sqlite_master` 确认能读写。

#### 2.4 事务处理：4 张表逐个 DELETE，中途失败会怎样？——**会出现"半清理"状态（无原子性）**

`MFKeychain.mm:109-134` 每张表各自 `sqlite3_exec`（默认 autocommit），没有 `BEGIN IMMEDIATE … COMMIT`。
- 失败在第 2 张表：第 1 张表的删除**已提交**，无法回滚 → 钥匙串里同一游戏的 `genp` 删了、`inet` 还在。
- 更糟的是回显：失败分支只 `NSLog`（L131），`res.error` 保持 nil → `RootViewController.mm:416-421` 会弹"删除 0 条"，**用户以为没删**，实际已删掉一部分。
- 修法：
  ```objc
  sqlite3_exec(db, "BEGIN IMMEDIATE", ...);
  // 4 张表 DELETE；任一失败 -> "ROLLBACK"，并把 sqlite3_errmsg 写进 res.error
  sqlite3_exec(db, "COMMIT", ...);
  // 结束时用同一条件重新 COUNT(*) 复核，若 >0 则明确报"未完全生效"
  ```
- 注意：SQLite 的 DDL/事务在本库上与 securityd 的并发行为【未证】，务必先在测试机验证；另外删除后 securityd 的内存缓存可能仍生效直到其重启（【推断】），建议 UI 上写清"可能需要重新登录/重启生效"。

#### 2.5 有没有先备份？——**没有（且原版也没有）**

- 复刻版：`MFKeychain` 全文件无备份逻辑【已证】。
- 对比：防封那条线至少有 `backupPlistWithError`（`MFAntiBan.mm:68-87`），而**破坏性更强的 keychain 删除反而没有**。
- 建议：删除前把 `/var/Keychains/keychain-2.db` + `-wal`/`-shm`（若存在）复制到 Documents（需 root 读权限；或者退一步：把"将被删除的 agrp/表/行数"导出成 JSON/CSV 落盘，作为最小可追溯证据）。同时 UI 必须给出"这会删除**全系统**钥匙串中匹配 agrp 的条目（Wi-Fi 密码、账号令牌等）"的警告——当前对话框只有技术描述（`RootViewController.mm:347-350`），没有损失面提示。

### ★ 三、高级游戏模式

#### 3.1 语义：读 `stat.st_mode & 0x80`，有=关闭、无=开启 —— **对【已证】**

与【游戏模式复核】表 1:1 对应（原文：`LDRH W8,[X8,#4]` / `UBFX W8,W8,#7,#1`）：

| 情形 | 原版 UI | 复刻 |
|---|---|---|
| stat 成功且 `&0x80 != 0` | 已关闭 | `isGameModeOn → NO`（`MFKeychain.mm:163`）→ "高级游戏模式已关闭"（L171） |
| stat 成功且 `&0x80 == 0` | ✅已开启 | `→ YES` → "✓ 高级游戏模式已开启"（L169） |
| stat 失败 | 也显示"已开启" | `return YES`（`MFKeychain.mm:158-162`） |

唯一建议：把"stat 失败"与"真的没有写位"在 UI 上分开（现在文案一样，会把"根本没权限/文件不存在"误报为"已开启"，这正是【游戏模式复核】明确提示的坑）。`keychainModeOctal == nil` 时 `gameModeStatusText` 会显示"（权限 ?）"（L167-171），可作为区分点，但没有明确文案。

#### 3.2 切换用 `chmod` 改 `~S_IWUSR` —— **方向合理，但有两个前提没满足**

- 原版：`posix_spawn` 自身 + **persona 99 / uid/gid 0** + `waitpid`，参数 `-Callrekyxms`（开）/`-Callregyxms`（关）；**具体 chmod 值【未证】**（【补充分析】§5、【功能账本】L26-32）。
- 复刻做法（`MFKeychain.mm:174-194`）：`cur = st_mode & 07777`；`开 = cur & ~0x80`；`关 = cur | 0x80`；直接 `chmod()`。
  - **合理性【推断】**：这是与"读语义只由这一位定义"最自洽、最保守、可逆的写法（保留其余位，只翻一位）。比硬编码 `chmod 000/600` 安全。
  - **前提 1（致命）**：`chmod` 要求**调用者是文件属主或 root**。实测 `权限 600` ⇒ 属主大概率是 root:wheel；mobile(501) 执行 `chmod` 必然 `EPERM(1)`。也就是说**该开关在目标机上永远失败**，与 P0-3 同源。修法：复刻原版的 uid-0 子进程（`posix_spawnattr_setuid_np/setgid_np/setpersona_np` + 专用 argv），并在 `main.mm` 里加这些 argv 的分支。
  - **前提 2（体验）**：没有"状态持久化/自动恢复"。原版警告反复强调"一定记得关闭"。建议：把切换前的原始 mode 落到 Documents；App 每次启动检查该位，若处于"已开启"就显著提示（甚至提供"一键恢复"），避免用户忘记后系统层面出现作者所说的"黑环境/白苹果"类风险。
- 另外一个诚实的评价：`errno` 文案里带了 `strerror`（`MFKeychain.mm:187-188`），失败时用户能看到"Operation not permitted"——这点做得对。

#### 3.3 风险：改 `keychain-2.db` 权限会不会让系统出问题？——**会，且当前没有告警外的兜底**

- 语义上：清掉属主写位 ⇒ 属主（root/securityd 相关写入路径）在**不检查 capability 的场景**里写不动该库 ⇒ 造成钥匙串写入失败（表现可以是登录态异常、App 反复要密码、系统设置项异常）。作者原话（"黑环境""关机重启会白"）出自【补充分析】§5，**是作者的风险描述，不是实测结论**（本报告同样不做定性）。
- 复刻版的风险控制现状：**只有弹窗文案**（`RootViewController.mm:471-478`，逐行与该 CFString 一致【已证】），没有：
  1. 前置"我需要 root"的可行性判断（其实可以在切换前先做一次 `chmod` dry 探测：`open(path, O_WRONLY)` 或 `access(path, W_OK)`）；
  2. 失败后的状态一致性说明（失败时 UI 会 toast，但状态行仍会把"stat 失败/无权"显示成"已开启"，见 3.1）；
  3. 崩溃/退出后的自动恢复。
- 修法建议：`isGameModeOn` 里区分 `stat` 失败；`setGameModeOn` 前先 `access(W_OK)` 判断权限并给出"需要 root（当前 uid=%d）"；把原始 mode 落盘并在启动时提示恢复。

### ★ 四、防封（lsdidentifiers.plist）

#### 4.1 实测"未找到" —— `MFPaths.lsdIdentifiersPlist` 的搜索路径对不对？（根因分析见 §四）

结论先行：**路径候选不全 + 错误被吞 + 权限门槛**三件事叠加，且分析报告只给了目录前缀 `/var/containers/Shared/SystemGroup`，**没有给出完整路径**（【补充分析】§5、【功能账本】L61），复刻版的 `Library/Darwin` 这一层属于**猜测【未证】**。

```
<GROUP>/Library/Darwin/com.apple.lsdidentifiers.plist
```

缺口：

2. 若真实位置带别的中间层（例如 `<GROUP>/Library/Preferences/`、`<GROUP>/Library/Cookies/`、`<GROUP>/Library/Caches/`），当前一律错过。
3. 若 `SystemGroup` 目录对 mobile 不可读（POSIX 权限，与沙盒无关），`contentsOfDirectoryAtPath:` 返回 nil，`for-in` 静默空转 → 直接 nil。

```objc
// 1) 保留原有候选，但同时做一次"限定深度"的目录遍历（而不是猜路径）
//    <GROUP>/Library 下深度 ≤ 3 内搜索文件名 com.apple.lsdidentifiers.plist

// 3) 控制台把 SystemGroup 的"可列出 / 条目数 / 权限"打出来（已有的自检行可以复用）
```
（真机候选实测清单与验证命令见 §四。）

#### 4.2 读-改-写流程与 plist 结构假设 —— **流程对；结构假设部分有依据、部分未证**

- 结构（`MFAntiBan.mm:11-14`）：`LSApplications` / `LSVendors` / `LSAdvertiserIdentifier` / `LSVendorIdentifier`：**有依据【已证】**（【功能账本】L61 明确列出这四个键名是原版解出的）。
- 层级假设：`LSApplications[bundleID] = {ida, idv}`、`LSVendors[uuid] = bundleID`：**是合理重建【未证】**。分析只证到"plist 里存在这些键"，没有证到嵌套形状；且原版重写链里出现了 `removeAllObjects` 与 `hasPrefix:`（【清理Key】§2 的 selector 全表）——说明原版**清空/过滤**过某些容器（很可能就是重建 `LSVendors`），复刻版是"增量更新"（`MFAntiBan.mm:145-148` 只清同 bundleID 的旧 vendor 键）。两种策略在结果上可能不同（原版可能清掉了所有旧映射）。
- 值语义：idv = ida = 同一个 UUID：**与【清理Key】§3.3 的结论一致**（"同一个统一值"），实现于 `MFAntiBan.mm:135-142` ✅。
- 写回：`NSPropertyListSerialization` → **XML 格式**（`MFAntiBan.mm:155-158`）→ `writeToFile:atomically:YES`（L163）。两个提示：
  - 原版的 `dataWithPropertyList:format:` 用的是哪个 format **【未证】**；如果原始文件是 binary，改成 XML 一般仍可解析（CFPropertyList 双格式支持），但**盘上格式变了**，属于"非必要变更"，建议保留原格式（读的时候记录 `format` 参数）。
  - `atomically:YES` 的语义是**临时文件 + rename**：新文件属主会变成当前进程（mobile），权限按 umask（通常 0644）——**不会保留原文件的属主/权限**。这在 SystemGroup 容器里意味着：① 目录不可写时直接失败；② 写成功后文件归 mobile 所有，可能改变系统对它的信任/写回关系；③ 与 lsd 自身写文件的竞态。建议改为"就地写 + 保留属主/权限"（`open(O_WRONLY|O_TRUNC)` 后写，或写入后 `chown/chmod` 还原）。
- 缺少：**写完读回校验**（重新解析并与期望值比对），以及**结果可见性**：`currentIdentifiersForBundleID:` 写好了却**零调用**（全工程仅声明+实现），所以"重置后到底改成什么"在设备上看不到。

#### 4.3 写坏这个文件会怎样？有没有备份回滚？——**备份有，回滚没有；坏文件的后果需要实测**

- 备份：`backupPlistWithError:` 复制到 `Documents/lsdidentifiers-backup-yyyyMMdd-HHmmss.plist`（`MFAntiBan.mm:68-87`），并且在改之前调用（`RootViewController.mm:430`）。
  - 问题 1：**返回值/错误被丢弃**（`NULL`）→ 备份失败也照样改。
  - 问题 2：**没有任何"从此备份恢复"的入口**（UI 只有"重置四个游戏"和"关闭"，`RootViewController.mm:439-447`）。回滚需要用户自己用 Filza 拷回，而目标机可能没有 Filza。
  - 问题 3：文件名用默认 `NSDateFormatter`（本地日历/时区），建议 `en_US_POSIX`。
- 写坏的后果评估：
  - 该 plist 是 LaunchServices 的**标识符缓存**。即使内容异常，launchservicesd 通常会在下次重建/补齐；最坏情况是相关 App 的 idv/ida 变化（这正是本功能的目标）或需要重启让 lsd 重建缓存。**"写坏=变砖"没有依据【未证】**。
  - 真正的风险在于**权限/属主被改**（见 4.2）与**写入期间 lsd 的竞态**（lsd 可能把内存里的旧状态重新落盘，覆盖我们的修改）。
  - 另一个隐含风险：**只保留 4 个游戏条目、不清理其它游戏/其它 App 的映射**——原版有 `removeAllObjects`/`hasPrefix:` 的痕迹，如果原版的意图是"把某个前缀下的全部旧记录清掉"，复刻版会留下"旧 ID → bundleID"的残留映射，可能影响效果。

#### 4.4 `killall lsd` 用 `popen` 可行吗？——**能跑，但不可靠；且失败被当成成功**

`MFAntiBan.mm:175-190`：
```objc
FILE *fp = popen("/usr/bin/killall -TERM lsd 2>&1", "r");
if (fp) { fgets(buf, …); pclose(fp); … return YES; }
```
问题：
1. **只判断 `popen` 是否成功**（=能否 fork/exec 一个 shell），**不判断 `killall` 的退出码**。权限不足时 `killall` 会打印 `No matching processes belonging to you were found` 或以非 0 退出，代码仍 `return YES` → 上层 `RootViewController.mm:449-462` 会弹"防封完成"，**谎报成功**。
2. **权限**：`lsd` 是系统守护进程（非 mobile 所有），mobile 身份 `kill` 它会 `EPERM`。所以这一步在目标机上大概率无效（P0-3）。
3. 只读一行输出（`fgets`），多行错误看不到。
更可靠的做法（择一）：
```objc
// A) 用 posix_spawn 直接执行 /usr/bin/killall，waitpid 取退出码（推荐，也顺手解决僵尸）
// B) 自己找 pid：proc_listallpids + proc_pidpath → kill(pid, SIGTERM/SIGKILL)，再校验存活
// C) 不 kill：写完 plist 后主动触发 LaunchServices 重新读取（或直接向用户说明"重启后生效"）
```
另外：`killall` 杀的是**所有**叫 `lsd` 的进程；如果设备上有多个同名的第三方进程，会被连带影响（低概率，但值得知道）。

#### 5.3 进程列表页"点进程绑定"：task port 在别的进程里还有效吗？需要 `mach_port_insert_right` 吗？

**核心结论：端口名是"进程私有 IPC 命名空间里的名字"，跨进程毫无意义；当前实现只写在本进程里，所以对 HUD 绘制进程完全无效。**

- 依据：`MFProcessViewController.mm:274` 把 `p.taskPort` 写进**本进程**的 `MFGameReader`；`MFGameReader.mm:28-31` 只是把它转给同进程的 `MFReadBackend`；HUD 进程从来没人调过 `setTargetTaskPort`，所以 HUD 里 `targetTaskPort == 0`（`MFReadBackend.mm:72-75` 门条件不成立）→ `MFDrawingLayer.mm:75` 直接 return。
- 关于"要不要 `mach_port_insert_right`"：
  - 端口**名字**（name）只在创建它的 task 的 IPC space 内有效。要从 A 进程传给 B 进程，必须走 **Mach IPC**：A 通过一个已注册到 bootstrap 的端口（`bootstrap_register` / `bootstrap_look_up`）向 B 发消息，把端口作为 `MACH_MSG_TYPE_MAKE_SEND`/`COPY_SEND` 描述符发过去；B 收到后其命名空间里就有这个名字（这一步是内核在收消息时插入右，不需要你自己 `mach_port_insert_right`）。
  - `mach_port_insert_right` 的用途是"把本进程已持有但尚未命名的 right 显式插入本进程命名空间"（例如通过 `mach_port_extract_right` 或 memory-object 拿到的 right）——**它不能凭空把端口插进别人的命名空间**。所以即使加了这行，也不会让 HUD 拿到可用端口。
- 两个可行修法（推荐第 1 个）：
  1. **让 HUD 进程自己完成"枚举 → task_for_pid → 读内存"**（原版就是"枚举与缓存端口"和"读取后端"在同一进程内，见【KFD链路】§八）。HUD 进程有同样的 entitlements（`task_for_pid-allow` / `platform-application`），拿到游戏的 pid 后直接 `task_for_pid(mach_task_self(), pid, &port)` 是最短路径；也可以用 `proc_listallpids` + `proc_pidpath` 自己找目标。
  2. 若坚持"主进程绑定、HUD 使用"，就必须补一套 Mach IPC（bootstrap 注册 + 端口传递 + 生命周期管理），工作量远大于方案 1，且要处理 HUD 重启后的重传。
- 附带一个必须一起改的点：`MFReadBackend`/`MFGameReader` 的"门条件"被实现成了"端口非空即 modeFlag=1"（`MFReadBackend.mm:77-81`），原版是**两个独立全局**（`qword_100FF7468` 与 `dword_100FF7470`，【KFD链路】§5.3）。语义被弱化但不影响正确性；不过建议至少把 `modeFlag` 的写入点收拢到一处，避免未来出现"端口没换但标志被置位"的竞态。

#### 5.4 `processor_set_tasks kr=0x4` 的候选原因（逐条假设 + 验证方法）

先说这条错误是从哪来的：`MFKernel.mm:371-374`
```objc
if (kr != KERN_SUCCESS || !tasks) {
    if (err) *err = [NSString stringWithFormat:@"processor_set_tasks kr=0x%x", kr];
```
`0x4 = KERN_INVALID_ARGUMENT`。按可能性排序：

| # | 假设 | 依据 | 验证方法 |
|---|---|---|---|
| **H1（主因，已由 API 契约证实）** | 路 B 传给 `processor_set_tasks` 的是**名字端口**（`processor_set_name_t`），而该调用要求**控制端口**（`processor_set_t): port_t`），内核转换失败即返回 `KERN_INVALID_ARGUMENT` | XNU `mach_host.defs`：`processor_set_default(... out default_set : processor_set_name_t)`；`processor_set.defs`：`processor_set_tasks(processor_set : processor_set_t)`。复刻版正是"`processor_set_default` → 直接 `processor_set_tasks`"（`MFKernel.mm:356-363` → `368`） | ① 看"能力探测"报告：若"路 B `processor_set_default` kr=0x0 ✓ 可用"，随后 `processor_set_tasks` 返回 0x4，即 H1 成立；② 交叉验证：在越狱/带 `host_priv` 的环境用 `host_processor_sets` + `host_processor_set_priv` 拿控制端口再调 `processor_set_tasks`，应当成功 |
| **H2（必然同时成立）** | `detectRoute` 先试路 B，**成功就返回**（`MFKernel.mm:252-259`），而 `processor_set_default` 对非特权进程也会成功 ⇒ 路 A 永远不会被尝试；因此**任何设备上都只会走到 H1 这条错路** | 代码顺序 + H1 | 在 `detectRoute` 里加日志打印 `pset/主机端口`，或临时把路 B 分支注释掉，看路 A 的 `host_processor_sets` / `host_processor_set_priv` 报什么（预期：`host_processor_set_priv` 失败 → 说明确实缺 `host_priv`） |
| **H3** | 即便用对了端口，**缺 `host_priv` 也拿不到控制端口**（原版的门槛就在 `host_processor_set_priv`，【KFD链路】§五/§八）：而 `host_priv` 要靠 `task_get_special_port(self, TASK_KERNEL_PORT)`（tfp0），非越狱/未打补丁时为 0（`MFKernel.mm:213-248`） | 【KFD链路】§四 | 看探测报告里 `TASK_KERNEL_PORT` 一行：`× 无` ⇒ H3 成立。此时"先跑 KFD"也不够：**复刻版没有任何"用 kread/kwrite 把 tfp0/host_priv 造出来"的后续步骤**（`kreadAddress:`/`kwriteValue:` 是死代码），所以 kopen 成功也依然拿不到 |
| **H4** | 参数/签名层面的低级错误（`task_list` 或 `count` 为 NULL、pset 为 `MACH_PORT_NULL`） | 代码看不存在：`tasks=NULL/taskCnt=0` 且 pset 已判空（`MFKernel.mm:359-362`） | 打点打印 `pset` 与两个出参地址；基本可排除 |
| **H5** | 沙盒/权限层拦截（mach lookup 被拒、`mac_proc_check`）——通常表现为 `KERN_INVALID_NAME(0x3)` / `KERN_DENIED` 而不是 0x4 | 与观测值不符 | 若换成 0x3/0x5 再考虑；可在 `probeCapabilitiesWithCompletion` 里把三处 kr 都打全 |
| **H6** | 目标机上 `processor_set_tasks` 因其他策略被禁（企业/MDM 配置、内核加固开关） | 无证据 | 对比同版本越狱设备上同一调用的返回值 |

**对 H1/H2 的最小修复建议**（去掉一条死路，明确一条活路）：
```objc
// 1) detectRoute：不要再把 processor_set_default 当"可用路由"
//    —— 它只证明"能拿到名字端口"，毫无用处
// 2) 路 A 才是唯一可能成功的路径：host_processor_sets → host_processor_set_priv(host_priv,…)
// 3) 先用短路径替代整个 pset 方案：
//      proc_listallpids()/sysctl(KERN_PROC_ALL)  →  目标 pid
//      task_for_pid(mach_task_self(), pid, &port)   ← entitlements 里已有 task_for_pid-allow
//    这条路不依赖 host_priv，正是原版另一条"独立模块基址路径"用到的能力
//    （原版导入表里就有 proc_listallpids / task_info / mach_vm_read_overwrite，
//      见【白米饭逆向分析报告】L68 与 evidence/data-offline-stubs.json）
// 4) 真要枚举全系统 task，再走 KFD：用 kread 走 kernel_task 的 tasks 链表，
//    而不是继续在用户态 Mach API 上撞运气
```

#### 5.5 资源泄漏（线程 / 定时器 / observer / fd）

| 类型 | 结论 | 依据 |
|---|---|---|
| Mach 端口右 | **有，严重** | `MFKernel.mm:376-401`：枚举成功时把 `tasks[i]` 存进 `MFProcessInfo.taskPort` 并**永不 deallocate**（只有失败分支 L382/L388 释放）。每次 `reload` 泄漏 N 个 task 控制端口右（N≈进程数）。持有右会让目标 task 的端口对象无法销毁 → 已退出进程的 task 结构无法释放（内核侧泄漏）。**注意**：`vm_deallocate(tasks,…)`（L401）只释放数组内存，不释放端口右。修法：给 `MFProcessInfo` 加 `dealloc`/显式 `releasePort`，或在页面 `dealloc` 时统一遍历 `all` 释放；绑定目标端口的那个右单独保留。 |
| 线程 | 无自建线程/定时器 | `MFOverlayView.mm` 只有 `CADisplayLink`；全工程 grep `addObserver/NSTimer/dispatch_source` = 0 命中 ✅ |
| 定时器（display link） | 生命周期未闭合 | `CADisplayLink` 强引用 target（`MFOverlayView.mm:84`），只有 `didMoveToWindow → stopRendering`（L60-68）会 `invalidate`。HUD 进程里窗口与进程同生共死 ⇒ 实际影响小；但若将来支持"动态关掉绘制窗"必须先 `stopRendering`。 |
| fd | 两处 | ① `mf_redirect_klog` 的 `g_klog_fd` 永不关闭（`MFKernelBridge.m:194-212`）；② `popen/pclose` 成对（`MFAntiBan.mm:179-183`）✅；③ SQLite 连接每次都 `sqlite3_close`（`MFKeychain.mm:97/135`）✅；④ `MFHUDLauncher` 的子进程继承父进程 fd（未设 CLOEXEC）。 |
| 内存 | 大体干净 | `mf_read_klog` 用 `malloc` → `MFKernel.mm:423-428` 用 `free` ✅（配套正确）；`MFKernel.kernelLog` 的字符串再被 UI 复制一份（可接受）。`MFOverlayView.tick:` 内有 `@autoreleasepool` ✅（`MFOverlayView.mm:105`）。 |
| 对象 | 一处隐患 | `MFOverlayView._imgui` 从不 `shutdown`（`MFImGuiContext.mm:60-67` 无调用者）→ ImGui 上下文/字体纹理/Metal 缓冲在"页面销毁"场景下泄漏。另外 `MFResidueViewController.rescan` 的 `self.scanning` 只防重入，不防"页面已出栈后回调仍 set 状态"（`MFResidueViewController.mm:99-119`，无 `isViewLoaded/weak self` 保护）。 |

## 四、实测问题的根因分析

### 4.1 `lsdidentifiers 未找到`

控制台这一行的渲染路径：`RootViewController.mm:121-125` → `MFAntiBan.plistPath`（`MFAntiBan.mm:27-29`）→ `MFPaths.lsdIdentifiersPlist`（`MFPaths.mm:24-37`）。

**候选原因（按可能性排序）**

| # | 候选 | 为什么可能 | 验证方法 |
|---|---|---|---|
| **H1** | **`/var/containers/Shared/SystemGroup` 对 mobile 不可列**（POSIX 权限，与 `no-sandbox` 无关）：`contentsOfDirectoryAtPath:` 返回 nil，`for-in` 静默空转 → 直接 `nil` | `com.apple.private.security.no-sandbox` 只豁免 sandbox（MACF 策略层），**不改变 VFS 权限判定**；SystemGroup 及其子容器多为 `root` 属主 | 控制台自检页已有 `pathRow:@"/var/containers/Shared/SystemGroup"`（`RootViewController.mm:155`）——**看它是 ✓ 还是 ×（读取失败）**；或在 `MFPaths.mm:27` 处把 NSError/errno 打出来（当前是 `error:NULL`） |
| **H2** | **完整路径候选不全**：真实文件不在 `Library/Darwin`、`Library/Caches/com.apple.lsd`、`Library` 这三层 | 分析只证到目录前缀 `/var/containers/Shared/SystemGroup`（【功能账本】L61），**没有证到中间层**；复刻版的 `Library/Darwin` 是猜的 | 在设备上用 Filza/SSH 直接在 `SystemGroup` 下 `find . -name 'com.apple.lsdidentifiers.plist'`；把命中路径写回候选表 |
| **H3** | **容器目录名不是 UUID 而是 `systemgroup.<identifier>` 形式**（本报告的乐观情形：其实不影响，因为循环遍历所有子目录） | 循环对 `groups` 的**每个**目录都试三种子路径，所以目录名形态本身不是障碍 | 同上（若 find 命中，说明 H1/H2 才是问题） |
| **H4** | 该 iOS 版本上文件**不在 SystemGroup**（例如落在用户域或另一个系统容器） | 不同 iOS 大版本位置会变；分析只覆盖了样本所在版本 | 全盘（非递归）搜索：`find /var -name 'com.apple.lsdidentifiers.plist' -maxdepth 6` |
| **H5** | 文件**存在但被平台保护**（`fileExistsAtPath` 需要父目录 `x` 权限，缺失即返回 NO） | 与 H1 同源，但表现为"目录列出来了、文件找不到" | 打点记录：`groups.count`、每个候选路径的 `access(F_OK)` 结果与 errno |
| **H6** | 文件名拼写/大小写差异（`com.apple.lsdidentifiers.plist` vs `lsdidentifiers.plist`） | 分析报告与原版字符串表都给的是带 `com.apple.` 前缀的全名【已证】 | `find … -iname '*lsdidentifier*'` |

**定位这件事的最小改动（不改功能）**：把 `lsdIdentifiersPlist` 改成"带回溯信息"的探测：
```objc
// 1) 目录列举失败 -> 记录 NSError + errno
// 2) 记录 (groups.count, 每个 group 下命中的第一个候选)
// 3) 控制台 "lsdidentifiers" 行改为显示：
//    "未找到（SystemGroup 可列=否 errno=13）" 或 "未找到（已列 47 项，3 个候选全无）"
```
**兼容性补强（建议）**：在 `<GROUP>/Library` 下做**限深遍历**（深度 ≤3，找同名文件），而不是死列三个路径；这能一次性覆盖 H2/H3/H6。

### 4.2 `processor_set_tasks kr=0x4`（KERN_INVALID_ARGUMENT）

见 §二-5.4 的六条假设。要点重述（因为这是本次审查最硬的一条结论）：

1. **H1 是已被 API 契约证实的必然失败**：`processor_set_default` 产出 **name port**，`processor_set_tasks` 要 **control port**。这不是权限问题、不是设备差异，**换任何设备、以 root 运行，路 B 都必然返回 `KERN_INVALID_ARGUMENT`**（除非内核被 patch）。
2. **H2 让它 100% 命中**：`detectRoute` 把"`processor_set_default` 成功"当作"路 B 可用"（`MFKernel.mm:254-259`），而它总是成功 ⇒ 代码永远走 H1 那条错路，路 A（唯一正确的形态）连一次都没被真正尝试过。
3. **H3 决定"修好路 B 也没用"**：路 A 的 `host_processor_set_priv` 需要 `host_priv`，复刻版只能从 `task_get_special_port(self, TASK_KERNEL_PORT)` 那条链去要（`MFKernel.mm:213-248`），非越狱下拿不到；而**复刻版没有"用 KFD 的 kread/kwrite 去换取 tfp0/host_priv"的任何代码**（`kreadAddress:`/`kwriteValue:` 是死代码）。

**建议的验收序列（真机，按顺序，都是只读/低风险）**
1. 点「能力探测」，抄录三行：`TASK_KERNEL_PORT` 的 kr/port、路 B `processor_set_default` 的 kr、`processor_set_tasks` 的 kr —— 这一份报告就能同时否掉/坐实 H1/H3/H5。
2. 对照 §1.4 的 `pathRow` 结果确认"沙盒豁免"是否生效（这决定 H1 类问题是否普遍存在）。
3. 换一条**不依赖 `host_priv`** 的枚举路快速验证可行性：`proc_listallpids()`（或 `sysctl KERN_PROC_ALL`）+ `proc_pidpath()` 先只做"列出进程"，再对目标 pid 试 `task_for_pid()`（entitlements 里已有 `task_for_pid-allow`）。这条路一旦通，"进程列表 + 绑定"立刻可用，`processor_set_tasks` 可以作为可选项后置。
4. 若确实需要全系统 task：走 KFD 用 `kread` 遍历 `kernel_task->tasks` 链表，拿 task 指针后再用 `task_for_pid` 落地成用户态端口（避免再把希望押在 `processor_set_tasks` 上）。

### 【已证】（本机可复算 / 有字节或源码依据）

1. `cleanup_rules.plist` 与逆向解出的原版**逐字节相同**（SHA-256 `b74c2ea6…`），25/108/334、default 分布与【配置复核】完全一致。

7. XNU MIG 定义：`processor_set_default` 出参为 `processor_set_name_t`，`processor_set_tasks` 入参为 `processor_set_t` ⇒ 路 B 恒失败（外部源码，非本机复算）。
8. `proc_pidpath(tasks[i], …)` 把 task port 当 pid 用（`proc_pidpath` 首参为 `pid_t`）。

### 【推断】（合理但未实证）

1. 目标机（TrollStore、非越狱、mobile=501）上：`chmod keychain-2.db` → `EPERM`；`sqlite3_open_v2(READWRITE)` → `SQLITE_CANTOPEN(14)`；写 SystemGroup 内的 plist → `EACCES/EPERM`。（预测的错误文本已写进 §二-2.3 / §二-3.2，便于实测对照。）

4. HUD 子进程不会被 FrontBoard 挂起（因此能在别的 App 上绘制）；主进程被强杀后子进程可能变孤儿。
5. `NSData writeToFile:atomically:YES` 的 rename 语义会改变 `lsdidentifiers.plist` 的属主与权限（不保留原文件的 root 属主/模式）。
