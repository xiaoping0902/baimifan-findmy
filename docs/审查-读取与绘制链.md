## 二、逐条明细

### 2.1 ★ 一、读取后端的正确性

#### 2.1.1 `mach_vm_remap` 参数与 `cur/max` 初始化 —— **基本正确，1 处边界隐患**

`MFReadBackend.mm:109-113` 的调用：

```c
kern_return_t kr = g_remap(mach_task_self(), &local, span, 0,
                           VM_FLAGS_ANYWHERE, self.targetTaskPort, aligned,
                           TRUE, &cur, &max, VM_INHERIT_NONE);
```

逐项对表（**链路 §七**、**分类 §1**、`evidence/read-backend-dec-0x1009d13a0.json` 原始反编译 11 参调用）：

| 形参 | 复刻值 | 分析报告 | 判定 |
|---|---|---|---|
| `target_task` | `mach_task_self()` | `mach_task_self_` | ✅【已证】一致 |
| `target_address` | `&local`（初始 0） | 本地输出指针 | ✅ |
| `size` | `span`（页对齐） | `pagesize` | ⚠️ 见下 |
| `mask` | `0` | `0` | ✅ 常量 |
| `flags` | `VM_FLAGS_ANYWHERE`(=1) | `1` | ✅ |
| `src_task` | `targetTaskPort`（= `dword_100FF7470`） | 缓存端口 | ✅ 链路 §六 |
| `src_address` | `aligned = remote & ~(page-1)` | 同式 | ✅ |
| `copy` | `TRUE` | `1` | ✅ |
| `cur/max` | `VM_PROT_READ` | 本地输出 | ✅ **写法正确**：XNU 的 `mach_vm_remap` 只在内部成功后回填，失败路径直接 `return`，所以"填 READ 再去读回"是安全的；用 `VM_PROT_NONE`(0) 初始化也是同类安全 |
| `inheritance` | `VM_INHERIT_NONE`(=0) | `2` | ⚠️ 见下 |

**⚠️ 隐患 1 · `size` 由 `pagesize` 变成 `span`（跨页支持）**

代码自称"请求长度跨页也要能读：算出要映射几页"（`MFReadBackend.mm:102`）、`docs/复刻版验证状态.md:226` 自称"还把跨页请求这个原版隐患补上了"。**但分析报告没证原版有跨页分支**：

- **链路 §七** 参数表写死 `size=pagesize`；`README` 式伪码也写 `memcpy(...)` 后 `mach_vm_deallocate(..., pagesize)`。
- **分类 §1.2** 写 `比较 偏移 + 请求长度 与页大小`；`evidence/read-backend-followup.md` 明确：`范围检查 | 比较 offset+requested_size > pagesize；后续分支由平坦化状态决定，本文不把所有跨页处理写成已证`。

⇒ 复刻版的 `span` 是**自己的扩展**，不是对齐。它本身不破坏单页语义（`span(pagesize)` 时等价），但要注意：
1. 原版很可能靠"**六种请求长度都远小于 16KB**"这一事实来避免跨页，所以**跨页支持永远不该被真正触发**。真触发了说明请求长度算错。
2. `span > pagesize` 时原版会**只映射第一页**——即"跨页请求在原版是未定义行为"。复刻版给了它定义，属于行为增强，需在文档里标成【推断】而不是"对齐"。

**修法**：保留 `span`，但在 `span != g_pagesize` 时打一条 `NSLog` 警告（正常情况下永远不该出现），并保留 `dealloc` 用同一个 `span`（已经在做了，`MFReadBackend.mm:120` ✅ 这点比上游还严谨）。

**⚠️ 隐患 2 · `inheritance` 传 0 而非 2**

实质差别为零（`VM_INHERIT_DEFAULT == VM_INHERIT_NONE == 0`，kernel 里 `switch (inherit) { case 0: case 1: ... }` 共路），但用了宏名会把 0 的含义写死进注释。**修法**：把注释改成"原版传 2（`VM_INHERIT_SHARE`），此处传 `VM_INHERIT_NONE`，两者都不影响本次 remap 的可读性；如需逐字节对齐原版可改成 `2`"。

#### 2.1.2 `mf_dealloc` 回退路径在地址 > 4GB 时的行为 —— **P0 反向问题：不是"会发生什么坏事"，而是"解除映射会失败且被静默丢弃"**

```c
// MFReadBackend.mm:37-40
static inline kern_return_t mf_dealloc(vm_map_t task, mach_vm_address_t addr, mach_vm_size_t size) {
    if (g_dealloc) return g_dealloc(task, addr, size);
    return vm_deallocate(task, (vm_address_t)addr, (vm_size_t)size);   // ← 32 位截断
}
```

- 正常路径 `g_dealloc`（`mach_vm_deallocate`）取 64 位，iOS 的 `mach_vm_address_t`/`mach_vm_size_t` 都是 `uint64_t`，`vm_map_t` 是 32 位 mach port 名。**这一路是对的。**
- 回退路径：`(vm_address_t)addr` 是 `uintptr_t`(64) → `uint32_t` 的**隐式窄化**。iOS 16/17 的用户态映射几乎必然落在 4GB 以上（`VM_FLAGS_ANYWHERE` 常从 `0x1_0000_0000+` 起分配），所以：
  - `vm_deallocate(0x1a2b3c000)` 实际执行 `vm_deallocate(0xa2b3c000)`；
  - 该地址大概率**未映射** → 返回 `KERN_INVALID_ADDRESS`；
  - **返回值被完全丢弃**（`MFReadBackend.mm:120` 不看 `kr`）→ 每次读取泄漏一页。一帧按 6 个封装 × 数十个实体的量级调用，泄漏速率是**每帧几十页 = 数百 KB/秒**。

- 更精确地说：`g_dealloc` 在 iOS 上**必然能取到**（`mach_vm_deallocate` 是 libSystem 导出的常规符号，非私有 framework），所以回退分支实际是死代码。但死代码里藏着上面那个坑，一旦哪天真机上 `dlsym` 返回 NULL（例如静态链接变体、或做了 `_mach_vm_deallocate` 名字不含下划线前缀的误判），就会**静默持续泄漏**而不是报错。

**修法**（任一）：
```c
// 方案 A：让回退路径显式失败
static inline kern_return_t mf_dealloc(...) {
    if (g_dealloc) return g_dealloc(task, addr, size);
    if (addr > 0xFFFFFFFFULL) {
        NSLog(@"[MF][Read] ⚠️ 无 mach_vm_deallocate 且地址 >4GB，映射无法释放（addr=0x%llx）", addr);
        return KERN_INVALID_ADDRESS;
    }
    return vm_deallocate(task, (vm_address_t)addr, (vm_size_t)size);
}
// 方案 B（更稳）：init 里声明 g_dealloc 必需，取不到就直接禁用 readRemote
if (!g_dealloc) { NSLog(@"[MF][Read] 致命：mach_vm_deallocate 不可用，读取后端停用"); return self; }
```
并把 `MFReadBackend.mm:120` 改成 `if (mf_dealloc(...) != KERN_SUCCESS) NSLog(...)`。

#### 2.1.3 `gateOpen` 逻辑 —— **语义等价于原版判据，但把两个独立全局绑成了一个（失去诊断能力）**

```c
// MFReadBackend.mm:72-81
- (BOOL)gateOpen { return self.modeFlag && self.targetTaskPort != MACH_PORT_NULL; }
- (void)setTargetTaskPort:(uint32_t)port {
    _targetTaskPort = port;
    self.modeFlag = (port != MACH_PORT_NULL);   // ← modeFlag 被反推
}
```

- **链路 §五.3**（`sub_10099A034`）已证判据是 `qword_100FF7468 == 1 && dword_100FF7470 != 0`，**两个独立全局**。其中 `0x100FF7468` 是**模式标记**（由模式选择回调 `sub_1009C8D90` 写 0/1，链路 §二），`0x100FF7470` 才是端口。
- 复刻版把 `modeFlag` 变成 `targetTaskPort` 的派生量 ⇒ `gateOpen` 塌缩成"端口非 0"。当前行为**看上去一样**，但：
  1. 丢掉"模式已选但端口未拿到（端口 0）"这个可观测状态，`statsText`（`MFReadBackend.mm:196-198`）里"门：开/关"就只剩端口这一个信息量；
  2. **存在一个真实的自相矛盾**：`MFProcessViewController.mm:274-275`
     ```objc
     r.targetTaskPort = p.taskPort;                 // 内部 modeFlag = YES
     [MFReadBackend shared].modeFlag = YES;          // 冗余，无害
     ```
     而 `MFGameReader.mm:28-31` 的 `setTargetTaskPort:` 在端口为 0 时会把 `modeFlag` 拽回 NO —— 这两处对 `modeFlag` 的所有权不清晰。
- 另：原门判还隐含"端口有效性"——原版 7 个写点只在 `host_processor_set_priv` 成功后写端口（**链路 §八.5**）。

**修法**：把 `modeFlag` 保持为独立属性（外部显式设置，不随端口联动），`gateOpen` 保持 `modeFlag && port`；在 `NSLog` 里分别打印两者，便于真机区分"没选模式"和"没拿到端口"。

#### 2.1.4 六个字节封装 vs 上游"读失败降级返回 0" —— **对齐，且比预想更严格**

**全解 §2.2** 已证六个封装的字节数 `8 / 12 / 4 / 48 / 12 / 12`，且"全部封装带 `FCSEL` 失败降级返回 0.0"；**分类 §2** 补充：8 字节封装"检查状态低 32 位为 0，并要求 outsize 等于 8，成功才返回值，否则返回 0"。

|---|---|---|---|---|
| `readU64` | 8 | `MFReadSizePointer=8` :19 | `.mm:128-142` | ✅ |
| `readFloat3` | 12 | `MFReadSizeFloat3/WorldPos/WorldPos2=12` :20,23,24 | `.mm:144-153` | ✅ 失败置三零 |
| `readFloat` | 4 | `MFReadSizeFloat=4` :21 | `.mm:155-159` | ✅ 失败返回 0.0f |
| `readCameraStruct` | 48 | `MFReadSizeCamera=48` :22 | `.mm:167-175` | ✅ 失败清零 |
| `readInt32` | —（原版没有这个封装，物资等级/价值走 4 字节请求） | — | `.mm:161-165` | ⚠️ 见 §2.1.8 |

**一个细节比报告语义更严格**：`readU64:out:` 在失败时**显式写 `*out = 0`**（`.mm:130-133`），而 `readFloat3/readCameraStruct` 走的是先读进本地 `tmp` 再拷出（`.mm:144-153,167-175`）—— 两种写法都等价于"调用者缓冲区最终为 0"，✅。

**同一函数名三个语义混用**（会咬人）：
```c
readU64:(uint64_t)addr                      // 失败 → 0
readU64:(uint64_t)addr out:(uint64_t *)out  // 失败 → NO 且 *out=0
readRemote:into:size:                       // 失败 → NO，缓冲区【不动】
```
`MFGameReader` 用的是第一种（如 `.mm:51,95,140`），`followChain` 用的是第一种+`==0` 断链（`.mm:184`），`readCamera` 用第二种（`.mm:51` 是第一种，`readEntities` 里 `item` 用第一种）。**混合使用会让"读失败"和"读到 0"永久不可区分**，见 G4。

#### 2.1.5 ★ `followChain:` 指针链语义 —— **链条解释错误（F3），这是"宏展开后语义不同"同类 Bug 的第二个实例**

```objc
// MFReadBackend.mm:179-189
- (uint64_t)followChain:(uint64_t)base offsets:(NSArray<NSNumber *> *)offsets {
    if (!offsets.count) return base;
    uint64_t cur = base;
    for (NSUInteger i = 0; i < offsets.count; i++) {
        uint64_t off = offsets[i].unsignedLongLongValue;
        uint64_t next = [self readU64:cur + off];   // ← 每一级都解引用
        if (next == 0) return 0;
        cur = next;
    }
    return cur;
}
```

调用侧（`MFGameReader.mm:46-47`）与官方文档的措辞（`MFReadBackend.h:72-73`「沿指针链逐级解引用（每级读 8 字节）」、`Offsets.h:120`）都是**"每级都是解引用"**。

**对照已证链**（**全解 §3.3**、【已证】9）：

```
obj + 0x98    → 读指针
     + 0x30   → 读指针
     + 0x408  → 读指针
     + 0x3A0  → 读指针
     + [全局 0x100FF65D0] + 0x10C0     ← ★ 动态偏移字段
     + 0x108  → 读
     + 0xF8   → 读
```

**链条里有两类步进，`followChain` 只实现了第一类：**

| 步 | 类型 | 正确语义 | `followChain` 实际做的 |
|---|---|---|---|
| `+0x98` | 解引用 | `cur = kread64(cur+0x98)` | ✅ 相同 |
| `+0x30` | 解引用 | 同上 | ✅ |
| `+0x408` | 解引用 | 同上 | ✅ |
| `+0x3A0` | 解引用 | 同上 | ✅ |
| **`[全局]+0x10C0`** | **加偏移（基准是另一个地址）** | `cur = kread64(kGlobal) + 0x10C0` | ❌ 做成 `cur = kread64(cur+0x10C0)` |
| `+0x108` | 解引用 | 同上 | ✅ |
| `+0xF8` | 解引用 | 同上 | ✅ |

⇒ 第 5 步**基址整个错了**：
- 正确基准是**游戏进程里的全局 `0x100FF65D0` 的当前值**（**全解 §七·推断 1** 认为是"版本/基址适配的动态偏移"，其上再加固定 `0x10C0`）；
- `followChain` 用的是**上一级解引用结果 `cur`**。

⇒ 后果：即使 `entityListBase` 校准到正确的链根，**从第 5 步起整条链走向一个不相关的地址空间**，`readCamera` 必然失败或读到垃圾（垃圾地址上的 `kread64` 还可能触发无效内存访问路径）。这是**和 `MFLibkfdKRead4` 同一个性质的问题**：调用名看起来"沿链解引用"没错，但链本身的定义里有一部分不是解引用。

**额外问题 A · 静态常量 0x10C0 会随游戏更新失效**（`Offsets.h:76-80` 对 `kMFLoot_Level/Value` 用了"运行时校准变量"，这里却把 `0x10C0` 硬写进 `rootChain`，标准不一致）。

**额外问题 B · 「最后一跳」被暴露给了错误的调用者**

`followChain` **返回最后一跳的解引用结果**（即 `kread64(...+0xF8)`），而报告把最后两项写的是「… → +0x108 → 读 → +0xF8 → 读」——**"读"意味着那里是数据字段，不是下一级指针**。所以：

- 若链根确实是实体对象，`followChain` 的返回值是"`+0xF8` 处的 8 字节数据"，**不是相机对象地址**；
- 若真要把"最后读到的值"当对象地址用，那链的多级结构还需要重新核对。

**这条【未证】**：报告没有给出 `sub_1001F9DB4` 段逐条指令的"解引用 vs 加偏移"标注（我只看到语义化的箭头串），也没有给出 `+0xF8` 之后的使用方式。所以**报告本身在这一段不是逐条已证的**，需要回 IDA 取原始字节再定。

**修法（把链改成可表达两类步进）**：

```objc
// 概念代码，不要直接照抄进仓库
typedef NS_ENUM(NSInteger, MFChainStepKind) { MFChainDeref, MFChainAddOffset };

@interface MFChainStep : NSObject
@property (nonatomic, assign) MFChainStepKind kind;
@property (nonatomic, assign) uint64_t value;      // deref: 偏移量；add: 偏移量
@property (nonatomic, assign) BOOL valueIsGlobal;  // deref: 该偏移来自"目标进程的某个全局"而非 cur
@end
```
或在保持 `NSArray<NSNumber*>` 的前提下加**负值编码约定**（`-1` = 结束不再解引用、`>=0` = 正常解引用、`-offset` = 加偏移不读）——不推荐，可读性差。

更稳的落地方式：
1. 把 `rootChain` 拆成 `rootChain`（纯解引用段）+ `dynamicOffsetSlot`（游戏进程内的全局地址）+ `dynamicOffsetAdd`（`0x10C0`）+ `tailChain`（`0x108 → 0xF8`）；
2. `followChain` 对每级**同时返回成功标志**，不允许用 0 表示失败；
3. 真机先只跑"前 4 级"，把每级结果打进 `NSLog`，与游戏实际对象地址对比，再定第 5 级。

#### 2.1.6 读失败时的统计/重试 —— **无死循环风险（【已证】），但有 3 处计数失真**

**【已证】无死循环**：全工程没有任何 `while` 重试读；`readRemote` 失败即 `return NO`（`MFReadBackend.mm:114-117`）；`MFGameReader` 的循环只有 `for (i < count)` 且 `count ≤ 4096`（`.mm:90,134`）。`MFLibkfdKRead4` 的循环是 `written < size` 且每轮至少写 1 字节（`MFKernelBridge.m:754,760-762`），**不会死循环**（但会空转，见 §2.3）。

**计数失真**：
1. `readRemote` 在门关时 `_failCount++`（`.mm:89-92`）—— 每帧 `ready==NO` 时不会有调用（调用方先判 `ready`），所以这条只在竞态下触发；
2. `readFloat3` 失败时**先**置零输出**再**返回 NO（`.mm:146-149`），调用方 `MFGameReader.mm:103-106` 还会 `[out addObject:e]` —— 即**一次失败被计一次 fail，但目标仍进数组**（对齐原版"画在原点"，见 §2.2.4）；
3. `readInt32` 失败**不区分**、返回 0（`.mm:161-165`），调用方无法计数。

**修法**：给 `readRemote` 加一个 `lastError` 输出（`kern_return_t` + `remote` 地址），`diagnosticReport` 里打印最近 10 条失败地址 —— 真机校准时这比"成功率"有用得多。

### 2.2 ★ 二、桥接层的 kread/kwrite 封装

#### 2.2.1 `size` 非 8 倍数会静默不做事 —— **确认存在，且桥接层的"兜底"确实修对了主路径**

宏证据（`kfd/libkfd/krkw.h:8-16`，与 `docs/_archive_kfd_upstream/.../krkw.h` 逐字节一致）：

```c
#define kread_from_method(type, method)                              \
    do {                                                             \
        volatile type* type_base = (volatile type*)(uaddr);          \
        u64 type_size = ((size) / (sizeof(type)));                   \
        for (u64 type_offset = 0; type_offset < type_size; type_offset++) { \
            type type_value = method(kfd, kaddr + (type_offset * sizeof(type))); \
            type_base[type_offset] = type_value;                     \
        }                                                            \
    } while (0)
```

`kread_sem_open_kread` 用 `kread_from_method(u64, kread_sem_open_kread_u64)`（`kread_sem_open.h:95`），`sizeof(u64)=8`：

| 传入 size | 展开后 `type_size` | 结果 |
|---|---|---|
| 4 | `4/8 = 0` | **一次不进，缓冲区原封不动** ← 用户发现的 bug |
| 12 | 1 | 只读到 8 字节，后 4 字节**静默丢弃** |
| 8 的倍数 | 正确 | ✅ |

`kwrite_from_method`（`krkw.h:21-29`）**同一个坑**：`type_size = size/8`，size=4 时写 0 次。

**逐条检查所有调用点的 size 参数：**

| 位置 | 调用 | size | 判定 |
|---|---|---|---|
| `MFKernelBridge.m:399` | `kread(kfd, kaddr, uaddr, size)` 整 8 倍数分支 | 由 `size & 7u == 0` 保证 | ✅ |
| `MFKernelBridge.m:418` | `kread(..., &chunk, sizeof(chunk))` 非 8 倍数分支 | `sizeof(uint64_t) = 8` | ✅ |
| `MFKernelBridge.m:454` | `kwrite(kfd, uaddr, kaddr, size)` 整 8 倍数分支 | 由守卫保证 | ✅ |
| `MFKernelBridge.m:484` | `kread(kfd, kaddr+done, &chunk, sizeof(chunk))` 局部读回 | 8 | ✅（但**返回值不查**，见 S2） |
| `MFKernelBridge.m:487` | `kwrite(kfd, &chunk, kaddr+done, sizeof(chunk))` | 8 | ✅ |
| `MFKernelBridge.m:530` | `kread(..., &chunk, sizeof(chunk))`（`mf_kread32` 兜底） | 8 | ✅（分支本身多余，N6） |
| `MFKernelBridge.m:553` | `kread(..., out, sizeof(*out))` | 8 | ✅ |
| `MFKernelBridge.m:584` | `kwrite(..., &slot, aligned, sizeof(slot))` | 8 | ✅ |
| `MFKernelBridge.m:602` | `kwrite(..., &value, kaddr, sizeof(value))` | 8 | ✅ |
| `MFKernelBridge.m:757` | `kread((u64)kfd, cur, &chunk64, sizeof(chunk64))` | 8 | ✅ **这就是那个 bug 的正确修法** |
| `MFKernelBridge.m:291` | `kopen(...)` | 非 kread | — |
| `kfd/fun/kpf/libdimentio.m:273` | `MFLibkfdKRead4((void*)kfd, addr, buf, sz)` | 任意 | ✅ 内部按 4 字节切片，见 §2.2.3 |

⇒ **主路径全部正确**，`MFKernelBridge.m:368-379` 那段"★★ kread/kwrite 的 size 必须是 8 的倍数 ★★"的注释和 `:395-433` 的分块实现是本文件里质量最高的一段。

**但仍有 3 个残留问题（P1/P2）：**

**(a) 尾部多读字节（S3）** `MFKernelBridge.m:428-431`：
```c
uint64_t take = size - done;
if (take > 8) take = 8;
memcpy(out + done, &chunk, (size_t)take);
```
`size=12` 时 `done=8`，`take=4`，但 `&chunk` 是**从 `kaddr+16` 读的 8 字节**。文档自己在 `MFKernelBridge.h:101-103` 写了"kread 在页边界可能连带读到上一页"，这里却**主动多读 4 字节**（`kaddr+16 .. kaddr+23` 越出调用者请求范围）。

**修法**：
```c
uint64_t take = size - done;
if (take > 8) take = 8;
/* 只读到 done 之后真正需要的字节；且不要越过请求末尾 */
uint64_t safe = take;
uint64_t pageLeft = 0x4000 - ((kaddr + done) & 0x3FFF);   /* 用 g_pagesize 更好 */
if (safe > pageLeft) safe = pageLeft;
if (safe == 0) { /* 跨页：退化成逐 4 字节读（MFLibkfdKRead4 的做法） */ }
```
更简单的做法：把最后一块改成逐 4 字节调用 `MFLibkfdKRead4`（它已经保证每个 4 字节读落在同一页内）。

**(b) 非 8 倍数分块读的页语义与上游不同**：上游是"**一次 64 位读**"（`kread_sem_open_kread_u64` 把 `pinfo` 指到 `kaddr - offsetof(pseminfo, psem_uid)`），所以**请求越小、越容易贴页首**；分块读会在 `kaddr, kaddr+8, …` 各做一次，**最后一页附近可能踩到"连带读上一页"**。已在 `MFKernelBridge.m:369-379` 的注释里承认了整体约束，但没有在分块循环里体现。属于**已知限制**，建议在注释里点明"分块读不享有 `kread_sem_open_kread_u32` 的页首保证"。

**(c) `size == 0` 提前 `return 0`（成功）**（`:391-393,446-448`）：语义上"什么都不做"和"成功"不能混。建议返回 0 但在 `g_err` 里留一条 trace，或直接返回 `-3 /* 空请求 */`。

#### 2.2.2 `mf_kread32` / `kread_sem_open_kread_u32` 这条特殊路径 —— **用对了，但兜底分支是错的**

`MFKernelBridge.m:509-539`：
```objc
if (g_kfd->kread.krkw_method_ops.kread == kread_sem_open_kread) {
    *out = kread_sem_open_kread_u32(g_kfd, kaddr);
} else {
    uint64_t chunk = 0;
    kread((u64)(uintptr_t)g_kfd, kaddr, &chunk, sizeof(chunk));   // 8 字节读
    *out = (uint32_t)(chunk & 0xFFFFFFFFu);
}
```

对照 `kread_sem_open.h:167-193`：
```c
u32 kread_sem_open_kread_u32(struct kfd* kfd, u64 kaddr) {
    ...
    u64 new_pinfo = kaddr - offsetof(struct pseminfo, psem_usecount);
    ...
    return *(u32*)(&data.pseminfo.psem_stat.vst_size);
}
```
注释（`:168-170`）明确："32-bit kread function that is guaranteed to **not underflow a page**, i.e. those 4 bytes are the **first 4 bytes** read by the modified kernel pointer."

⇒ **`mf_kread32` 的主路径选择是对的**，且它比 `kread(..., 4)` 安全得多。**但兜底分支（`else`）是错的**：
- 走"读 8 字节再截断"，等价于 `kfd->kread.krkw_method_ops.kread` 不是 sem_open 时的**唯一可用手段**，然而它会踩到"连带读上一页"——文档 `MFKernelBridge.h:101-103` 自己警告过。
- 更关键：**这个分支在 16.3+ 永远不可达**（`mf_kopen` 在 `MFKernelBridge.m:272-276` 直接拒绝 `kqueue_workloop_ctl`），所以它是"为了旧系统保留但会踩旧系统才有的坑"的死代码。

**修法**：`else` 改成
```c
mf_strlcpy(g_err, sizeof(g_err), "mf_kread32: 当前 kread 后端不是 sem_open，请改用 mf_kread64 并自行处理页边界");
return -3;
```
或直接 `mf_kread64(kaddr & ~7ULL, &chunk)` 后按 `kaddr & 7` 取高位——但要把"可能跨页"写进注释。

**顺带纠一条文档**：`MFKernelBridge.h:116`「便捷读写（内部保证不跨页边界的 4 字节读法）」——**只有 `mf_kread32` 保证**；`mf_kread64`（`:541-560`）就是普通 8 字节读，**没有**页边界保证。建议拆开描述。

#### 2.2.3 `MFLibkfdKRead4` —— **已修对，是本文件里最正确的实现**

`MFKernelBridge.m:745-764`：
```c
for (uint64_t cur = kaddr; written < size; cur += 4) {
    uint64_t chunk64 = 0;
    kread((u64)kfd, cur, &chunk64, sizeof(chunk64));  // 读 8 字节（必须）
    const unsigned char *b = (const unsigned char *)&chunk64;
    for (int i = 0; i < 4 && written < size; i++) out[written++] = b[i];
}
```
- `sizeof(chunk64) = 8` → `type_size = 1` → **循环会进** ✅
- 每次只取低 4 字节（小端 = 低地址 4 字节）✅
- 与上游 `early_kread32 → early_kread64` 等价 ✅
- 步进 4 字节，配合 `kread_sem_open_kread_u64` 的 `pinfo = kaddr - offsetof(pseminfo, psem_uid)` → 4 字节读落在页内 ✅

**唯一残留**：`kread` 无返回值（`libkfd.h:228-231` → `krkw_kread` 无返回），读失败时 `chunk64` 保持 0，函数**静默返回 0 数据**。`libdimentio.m` 的调用者（`kread_buf_kfd`）拿不到错误信号，patchfinder 会把 0 当成真实数据（`mach_header_64.magic != MH_MAGIC_64` 才报错，这点运气成分很高）。**修法**：加个 `int *ok` 出参，或让 `MFLibkfdKRead4` 返回最后一次 `kread` 前置状态（libkfd 没有），最实际的是在 `libdimentio.m` 侧对关键读单独调 `mf_kread64` 校验一次。

#### 2.2.4 所有 `kread`/`kwrite` 调用点 size 汇总 + `mf_kwrite32` 写 0 —— **确认：写 0 不但没写成，还会返回成功**

**(1) 上层调用点（`MFKernel.mm:476-484`）**
```objc
- (BOOL)kreadAddress:(uint64_t)kaddr into:(void *)out size:(uint64_t)size {
    if (![self isOpen]) return NO;
    return mf_kread(kaddr, out, size) == 0;
}
- (BOOL)kwriteValue:(const void *)in toAddress:(uint64_t)kaddr size:(uint64_t)size {
    if (![self isOpen]) return NO;
    return mf_kwrite((void *)in, kaddr, size) == 0;   // ← in 是 const，强转丢 const
}
```
- size 全部由调用者决定 → **这个文件里没有非 8 倍数调用点**【已证】。
- 且这两个方法**全工程无调用者**（见 §三）。
- `(void *)in` 去 const 是 `kwrite` 形参不 const 造成的，**不是 bug**，但会用"我承诺不写"的假象骗过读者；建议桥接口加 `const void *uaddr`（`kwrite_from_method` 只读 `type_base[type_offset]`，天然 const-safe）。

**(2) `mf_kwrite32` 写 0 —— 三层结论**

```objc
// MFKernelBridge.m:566-591
uint64_t aligned = kaddr & ~0x7ULL;
int shift = (int)((kaddr - aligned) * 8);
if (mf_kread64(aligned, &slot) != 0) return -1;
slot = (slot & ~(0xffffffffULL << shift)) | (((uint64_t)value) << shift);
kwrite((u64)(uintptr_t)g_kfd, &slot, aligned, sizeof(slot));
return 0;   // ← 恒成功
```

对照 `kwrite_dup.h:94-119`（`kwrite_sem_open` 直接转调它，`kwrite_sem_open.h:45-51`）：
```c
void kwrite_dup_kwrite_u64(struct kfd* kfd, u64 kaddr, u64 new_value) {
    if (new_value == 0) { print_warning("cannot write 0"); return; }        // ← ①
    ...
    u64 old_value = 0;
    kread((u64)(kfd), kaddr, &old_value, sizeof(old_value));
    if (old_value == 0) { print_warning("cannot overwrite 0"); return; }    // ← ②
    if (old_value == new_value) break;                                      // ← ③
    ... syscall(SYS_change_fdguard_np, ...) ...
}
```

三层：
1. **① `new_value == 0` 直接 return**：真写不进去。
2. **② `old_value == 0` 也 return**：即使你要写的是**非 0**，只要目标当前是 0（典型：未初始化字段、刚清零的指针），也写不进去。**这一条比用户提示里说的"不能写 0"更狠**，且上游 writeup 只提了 ①（`docs/kfd-移植清单.md:740-756`、`docs/kfd-集成调研.md:216`）。
3. **③ `old_value == new_value` 直接 break**：**返回值仍然是 void，调用方无从知道到底做没做。**

⇒ `mf_kwrite32(kaddr, 0)` 的可达性分析：
- `slot` 的另外 32 位（相邻字段）非 0 ⇒ `slot != 0` ⇒ 绕过 ① ⇒ `old_value` 也非 0 ⇒ 绕过 ② ⇒ **写成功**。这就是 `docs/kfd-移植清单.md:758-760` 里那段【推断】描述的效果，**这次可以从代码上确证它成立**：
  - `kaddr & 7 == 0`（低 4 字节）时，`slot` 高 32 位来自 `kaddr+4`；
  - `kaddr & 7 == 4`（高 4 字节）时，`slot` 低 32 位来自 `kaddr-4`。
- 两个相邻字段**同时**为 0 ⇒ `slot == 0` ⇒ 命中 ① ⇒ 静默失败。

⇒ **`mf_kwrite64(kaddr, 0)` 恒失败**（除非 `old==new==0`，那时命中 ③ 也什么都没做）——两条路都"成功返回"。

**修法**：
```c
int mf_kwrite64(uint64_t kaddr, uint64_t value) {
    if (value == 0) {
        mf_strlcpy(g_err, sizeof(g_err),
                   "mf_kwrite64: libkfd 无法写 0（kwrite_dup.h:96）—— 改用非零哨兵/等价改法");
        return -3;                       // ← 显式失败，不要静默
    }
    uint64_t old = 0;
    if (mf_kread64(kaddr & ~7ULL, &old) == 0 && ((kaddr & 7) ? (old >> 32) : (old & 0xFFFFFFFF)) == 0) {
        /* 目标槽内该半区为 0：底层会命中 "cannot overwrite 0" */
        mf_strlcpy(g_err, sizeof(g_err), "mf_kwrite64: 目标槽对应半区为 0，底层将拒绝写入（返回码不可信）");
        return -3;
    }
    ... 原逻辑 ...
}
```
并在 `MFKernelBridge.h:106-113` 把"不能写 0"扩写成"**不能写 0，也不能把 0 改成非 0**"。

#### 2.2.5 `mf_kwrite` 非 8 倍数分支不检查 `kread`（**S2**）

`MFKernelBridge.m:480-496`：
```c
if (setjmp(g_fail_jmp) == 0) {
    g_fail_armed = 1;
    if (partial) {
        kread((u64)(uintptr_t)g_kfd, kaddr + done, &chunk, sizeof(chunk));  // ← 无返回可查
    }
    memcpy(&chunk, in + done, (size_t)take);
    kwrite((u64)(uintptr_t)g_kfd, &chunk, kaddr + done, sizeof(chunk));
    ...
```
- `kread` 是 `void`（`libkfd.h:228`），**拿不到成功与否**；读失败 → `chunk` 保持 0 → `memcpy` 覆盖 4 字节后 `chunk` 可能仍为 0 → `kwrite` 命中 `cannot write 0` → **静默 no-op，函数返回 0（成功）**。
- 注释（`:468-469`）自称"这里会读回 0 再写回 0，可能失败 —— **如实返回错误**"，但代码没有任何"如实"的路径。

**修法**：改成显式两步、用有返回值的接口：
```c
if (partial) {
    uint64_t old = 0;
    if (mf_kread64(kaddr + done, &old) != 0) return -1;   // ← 有返回值
    chunk = old;
}
memcpy(&chunk, in + done, (size_t)take);
if (chunk == 0) { g_err = "...cannot write 0..."; return -3; }
kwrite(...);
```

#### 2.3.2 横向/纵向分量补全 —— **独立验算：正交性与透视除法自洽（✅），但用到具体游戏坐标时是"约定依赖"的（⚠️）**

代码（`MFProjection.mm:61-72`）：
```c
float depth = dx * cosP * cosY + dy * cosP * sinY + dz * sinP;
float side  = -dx * sinY + dy * cosY;
float up    = -( -dx * sinP * cosY - dy * sinP * sinY + dz * cosP );
```

**验算 F（前向）**：`F = (cosP·cosY, cosP·sinY, sinP)`
- `|F|² = cos²P·cos²Y + cos²P·sin²Y + sin²P = cos²P(cos²Y+sin²Y) + sin²P = cos²P + sin²P = 1` ✅ 单位向量
- `depth = d·F` ✅ **与全解 §5.1 步骤 4 逐字符一致**（已证式子）

**验算 R（右向）**：`R = (-sinY, cosY, 0)`
- `R·F = -sinY·cosP·cosY + cosY·cosP·sinY + 0 = 0` ✅ 正交
- `|R| = 1` ✅
- 方向：`F` 在 XZ 分量上为 `(cosY, sinY)`，把 `(x,z)` 平面逆时针转 90° 得 `(-sinY, cosY)` ⇒ `R` 是 `F` 在水平面内**逆时针 90°**。在**右手系**（Y 上、XZ 为地平面）里，这个方向是"朝左"而非"朝右"——所以代码里 `negateSide = YES`（`.mm:74`）是在把它掰回屏幕右方。**逻辑自洽** ✅。

**验算 U（上向）**：`U = (-sinP·cosY, -sinP·sinY, cosP)`
- `U·F = -sinP·cosY·cosP·cosY - sinP·sinY·cosP·sinY + cosP·sinP = -sinP·cosP(cos²Y+sin²Y) + cosP·sinP = 0` ✅ 正交
- `|U| = 1` ✅
- `U` 是 `F` 绕 `R` 转 +90°：符合"上 = 前 × 右"的右手约定 ✅

**验算投影轴**：
```c
x = centerX + focal · (side/depth)     // side 已含 negateSide
y = centerY + focal · (up/depth)       // up = -d·U ⇒ 屏幕 Y 向下
```
- 屏幕 Y 向下、`up = -d·U` ⇒ `z > camera.z` 的目标得到**更小的 y**（屏幕更上方）⇒ **向上为正** ✅ 自理
- 与深度公式**同源自洽**：`(side, up, depth)` 是 `d` 在标准正交基 `(R, -U, F)` 下的坐标，屏幕坐标 = 中心 + `focal·(横向/深度, 纵向/深度)` —— 与全解 §5.1 步骤 6 的形态**完全同构** ✅

⇒ **结论：两处分量式补全在数学上正确、与已证深度公式自洽。**【推断】

**⚠️ 但它是"约定依赖"的**（必须标清，否则真机上会误判为 bug）：
1. **`negateSide` 的取值等价于"世界坐标系手性 + 偏航零点"这两个未知量**。若目标游戏是左手系（`yaw` 从 +X 向 +Z 或反向计），则 `R` 的符号要翻——这正是 `MFSignConvention` 存在的原因，**设计正确**（`MFProjection.h:20`「若真机画面上下/左右镜像，改 MFSignConvention 即可」）。
2. **`roll` 的符号**：`.mm:78-83` 的旋转矩阵把 `(side, up)` 按 `+R` 旋转。物理上屏幕平面内的旋转是 `-roll`（相机滚 `+roll` 时世界看起来滚 `-roll`）。**`分类 §3` 明确：算法主体只用俯仰+偏航**（全解 §七·推断 3）⇒ **`applyRoll = YES` 很可能引入原版没有的旋转**。建议默认 `NO`（N2），真机若发现画面倾斜不对再开。
3. **`convention` 的默认值与头文件注释不符**：
   - `MFProjection.h:47-48`：「默认全 YES」
   - `MFProjection.mm:15`：`{.negateSide = YES, .negateUp = NO, .applyRoll = YES}`
   - 两个数不一致 ⇒ 以后按注释改代码的人会踩坑（N3）。

#### 2.3.3 边界情况

| 情况 | 现状 | 判定 |
|---|---|---|
| **FOV = 0** | `.mm:29` `fov <= 0 → tanf(π/4) ≈ 1.0` | ✅ 与 **全解 §5.1** 步骤 6、**分类 §3.5** 一致 |
| **FOV 极小（>0）** | `tanf(≈0) → ~1e-7`，`inv = focal/depth` 极小 ⇒ 所有目标挤到屏幕中心 | ⚠️ **未处理**。原版同样没处理（FOV≤0 才算异常），所以这是"继承的限制"。建议：`focal < 1e-3` 时按"投影无效"处理 |
| **FOV 负** | `.mm:29` 走 `tanf(π/4)` | ✅ |
| **相机在目标位置**（`d = 0`） | `depth = 0 < 0.1` ⇒ 返回哨兵 ✅ | ✅ 正确 |
| **深度为负（目标在背后）** | `depth < 0.1` ⇒ 返回哨兵 | ✅ 与全解同一判据（同一个 `fcmp/cset mi` 语义） |
| **深度刚好 0.1** | `0.1 < 0.1` 为假 ⇒ **放行**，`inv = focal/0.1 = 10·focal` ⇒ 坐标可达 `±10⁴·focal` 量级 | ⚠️ **未处理**，见 N1 |
| **屏幕尺寸为 0** | `MFDrawingLayer.mm:66` 已挡（`size.width < 1 \|\| size.height < 1 → return`）；`MFOverlayView.mm:100` 也挡 | ✅ |
| **目标坐标为 NaN/Inf** | 未处理 ⇒ `depth` 为 NaN ⇒ `NaN < 0.1` **为假** ⇒ **走完整个投影**，`x/y` 为 NaN ⇒ 进 ImGui DrawList | ⚠️ 见下 |

**NaN 路径的具体后果**：`MFDrawingLayer.mm:102-105` 判的是 `e.isVisible`（= `screen.valid`），NaN 情况下 `valid = YES`（`.mm:89`），于是 `drawEntity` 用 `e.screen.x = NaN` 建 `ImVec2`。ImGui 的 `AddRect` 对 NaN 坐标通常不崩但会产生巨大/畸形图元，某些后端会 `assert`。**修法**：
```c
if (!(depth >= kMF_MinDepth)) return out;              // NaN 也不通过
...
if (!isfinite(out.x) || !isfinite(out.y)) { out.x = out.y = kMF_Sentinel; out.valid = NO; return out; }
out.valid = YES;
```
注意 `if (depth < kMF_MinDepth)` 与 `if (!(depth >= kMF_MinDepth))` 对 NaN 的差别 —— **前者放行 NaN，后者拦截**。这是又一个"看上去对、语义不同"的实例，和用户要的 bug 同类。

#### 2.4.1 每帧四步调用顺序 —— **顺序对，但缺了一步"实体列表解析"**

原版（**全解 §一**）：① 读相机 → ② 数实体 → ③ 逐个投影 → ④ 画。

复刻版（`MFGameReader.mm:185-201` + `MFDrawingLayer.mm:75-117`）：
```

  screenWithSize:fov:  ← 派生

overlayBuildUI:

```
✅ **①→②③→④ 的顺序正确**，且相机失败时短路上游（`MFDrawingLayer.mm:78-79`）。

**⚠️ 但 `readCamera` 的取址方式与报告不符【已证】不一致**：
```c
// MFGameReader.mm:44-52

uint64_t camObjPtr = base + off.current.cameraPtrOffset;
uint64_t camObj = [rb readU64:camObjPtr];
```
注释（`:44-45`）写「按档案里的偏移直接走对象链」，但 **全解 §3.1** 已证相机有**两条路径**：
- 【路 1 · 远程】`X0 = 相机对象 + *(0x100FF6610) + 0x1890`（读 3 float）、`+0x18A0`（读 3 float）、`+0x18AC`（读 1 float）

复刻版实现的是**路 2 的布局**（`kMFCamera_X=0x10` … `kMFCamera_FOV=0x2C`），但**路 1 的三个远程地址（`+0x1890/0x18A0/0x18AC`）完全没实现**，而 `*(0x100FF6610)` 这个"相机对象基址"全局也没实现（`Offsets.h:91` 只是把它记在 `MFOriginalGlobals` 里当文档）。

⇒ 真机大概率要用**路 1**（路 2 是"加固/权限被拦时的降级"）。**这是缺少一条实现，不是 bug**，但文档要说清。

#### 2.4.2 物资的两个错误处理分支 —— **与报告一致（【已证】）**

**分类 §2**：「物资业务的两次 4 字节请求分别读取等级和价值。**错误处理不同**：价值读取失败、长度不等于 4 或结果为 0，会提前跳过；等级读取失败或长度不等于 4，则把等级置为 0」。

对照实现：
```c
// MFGameReader.mm:147-161
int32_t value = 0;
if (off.current.lootValueOffset &&
    ![rb readRemote:item + off.current.lootValueOffset into:&value size:4]) {
    continue;                       // ← 价值：读失败 → 跳过 ✅
}
if (value == 0) continue;           // ← 价值为 0 → 跳过 ✅
e.value = value;

int32_t level = 0;
if (off.current.lootLevelOffset) {
    [rb readRemote:item + off.current.lootLevelOffset into:&level size:4];  // ← 返回值忽略
}
e.level = level;                    // ← 等级：读失败 → 0，进默认色分支 ✅
```
✅ **两个分支的语义完全对齐**。选色侧（`MFDrawingLayer.mm:217-228`）也对齐了 **分类 §4 颜色分组表**（等级 3–6 走四项表，其余走 `value > 9999` → 3 级色，再否则 0–2 级色）。

**⚠️ 但真机上这两个分支当前永远不执行**（F1+F2）：`lootValueOffset == 0` ⇒ 第 149 行整条短路 ⇒ `value` 保持 0 ⇒ 第 153 行 `continue`。**`if (offset)` 这个守卫把"未校准"和"合法偏移 0"绑在一起了**——虽然字段偏移不可能是 0（对象头一般是 isa 指针），但它让"未校准"变成"静默跳过全部物资"，而不是"报未校准"。建议：
```c
if (off.current.lootValueOffset == 0 || off.current.lootLevelOffset == 0) {
    static dispatch_once_t once;
    dispatch_once(&once, ^{ NSLog(@"[MF][Read] 物资字段偏移未校准，物资链跳过（Offsets.h kMFLoot_*）"); });
    return out;
}
```

**另一处**：等级负值/大值都按"默认分支"处理（`.mm:161` 原样赋），选色侧再夹一次 `[3,6]`（`MFDrawingLayer.mm:219`）✅ 安全。但 `.mm:214` 的等级过滤写 `e.level > 0 &&` —— 负等级**绕过**过滤（**分类 §4** 明确"不能省略正值条件"），✅ 与报告一致。

#### 2.4.3 `entityListBase` / `lootListBase` 默认为 0 时是否安全失败 —— **安全（不崩），但失败点比设计意图更靠前**

```c
// MFGameReader.mm:85-86, 130-131
uint64_t base = [self resolveEntityListBase];
if (!base) return out;                       // ← 安全返回空数组
```
✅ 不崩。

但**实际默认值是 0**（见 §一 F1），所以：
1. `readCamera` → `followChain(0, chain)`：`readU64(0 + 0x98)` → `readRemote(0x98, …)`。**注意：这里没有 `!base` 判断**（`MFGameReader.mm:46` 直接进 `followChain`）⇒ 会**向目标进程的 0x98 处发起一次真实读取**。`mach_vm_remap` 对未映射地址返回 `KERN_INVALID_ADDRESS` ⇒ 安全返回 NO ⇒ `followChain` 返回 0 ⇒ `readCamera` 返回 NO。✅ 不崩，但**访问了无意义地址**。
2. `readEntities` / `readLoot` 因 `if (!base) return out` 直接返回。✅

**修法**：`MFGameReader.mm:46` 加 `if (!self.entityListBase) return NO;`，避免对 0 附近发起真实 remap（`mach_vm_remap` 对 `src_address = 0x98` 每次都要走一遍 VM 层，白烧时间）。

#### 2.4.4 循环边界 `count > 4096` —— **不会越界（✅），但语义上是个未证的上限**

- `count` 来源：`readInt32`（**全解 §3.2** 已证 `+0xE68` 是 int，`LDRSW X8,[X22,#0xE68]` 有符号加载）
- 守卫：`if (count <= 0 || count > 4096) return out;`（`.mm:90,134`）
- 数组访问：`base + 0x8 * (uint64_t)i`，`i ∈ [0, 4095]` ⇒ 最高达 `base + 0x7FF8`，**一页内，不越界** ✅
- `count` 字段本身在 `+0xE68`，**高于**数组区 ⇒ 无自我覆盖 ✅
- `loot` 侧的 `count` 复用 `entityCountOffset`（`.mm:133`）—— **【未证】**：分析报告只说"实体数量在 +0xE68"，**没有说物资列表也用这个偏移**。物资列表的数量字段偏移是另一个未证项（和 `lootLevelOffset/lootValueOffset` 同批）。**代码里没标注这一点，属于隐性假设。**

**修法**：
1. `MFGameProfile` 加 `lootCountOffset` 字段（默认 0 = 取消限制/未证）；
2. 把 `4096` 提成 `kMFEntityCountMax` 常量并在注释里写"防御上限，非原版限制；真机实测若 >4096 需提高"；
3. 循环里加 `if (i > 200 && [out count] == 0) break;` 之类的短路（当前 `count` 是垃圾值时最多浪费 4096 次 remap，每次 remap 都是页级操作，代价不低）。

#### 2.4.5 `@autoreleasepool` 位置 —— **位置正确（✅）；但缺一个更大粒度的池**

```c
for (int i = 0; i < count; i++) {
    @autoreleasepool {       // ← .mm:93 / :139

        MFEntity *e = [[MFEntity alloc] init];

        [out addObject:e];

```
- 每轮一个池 ⇒ 每轮的临时 `MFEntity`（非 addObject 的）及时回收 ✅
- `[out addObject:e]` 的对象逃出池，被 `out` 持有 ✅ 正确

**(a) `LOAD_NUM` 的强制转型会把 bool 当数字读**

`backEnemyStyle` 是 `NS_ENUM(NSInteger)`，`:172` 用 `doubleValue` 再转 enum —— 数值 0/1/2 没问题，但如果 plist 被手工改成一个非枚举值（如 `99`），`MFMenuUI.mm:198-200` 的 `(int)s.backEnemyStyle` 传给 `ImGui::Combo(..., styles, 3)`，**越界读 `styles[]`**。**修法**：加 `clamp`。

**(b) `init` 里 `resetToDefaults` → `load` 的顺序正确**（`:21-22`），保证任何缺失字段有默认值 ✅。但 `load` 失败（文件不存在）时返回 NO 被丢弃（`:22`），**没有任何日志**——真机上"配置没生效"时无从判断。**修法**：`if (![self load]) NSLog(@"[MF][Settings] 无配置文件，用默认值");`

- `bundleID`（`:111`）/ `displayName`（`:112`）—— **不持久化，且不该持久化**（是档案元数据）✅ 可接受

| **`span` 算术溢出** | `MFReadBackend.mm:103` | `(offset + size + g_pagesize - 1) & ~(g_pagesize-1)`：`offset ≤ 0x3FFF`、`size` 由调用者给。`remote` 接近 `UINT64_MAX` 时整体回绕 ⇒ `span` 变小 ⇒ `memcpy(out, local+offset, size)` **越界读**。**修法**：`if (remote > UINT64_MAX - g_pagesize*2 - size) { _failCount++; return NO; }` |

## 五、修复优先级建议（按"能让人看到画面"排序）

1. **F1+F2+F4**：给 `MFGameReader` 加两个真实写点（校准面板 / 或从 `MFOffsets` 读），并把 `rootObject` 与 `entityList` 拆开。这是**当前唯一挡住"能看到任何东西"**的墙。
2. **F3**：把 `followChain` 改成能表达"解引用 / 加偏移"两类步进；真机先打印每一级结果。
3. **S1+S2**：让 `mf_kwrite*` 在写 0 / 目标为 0 时**返回显式错误**（别再骗调用者）。当前没有调用者，但一旦写内存的功能接上就会踩。
4. **S5**：决定 HUD 是"同进程双窗口"（对齐原版，改架构）还是"HUD 子进程自己跑一遍 KFD+枚举+绑定"（改流程）。**当前两端都没做。**
5. **S4**：`proc_pidpath` 前面插一次 `pid_for_task`（顺手的事，收益是枚举从"可能全空"变成"确定能用"）。
6. **S6**：`detectRoute` 改成真正探测 `host_processor_set_priv` 能否成功，否则"路 A / 路 B"的显示是误导。
7. **G1**：`mf_dealloc` 的回退分支——要么删（要求 `g_dealloc` 必存在），要么加 `>4GB` 显式失败。**这是当前唯一的持续性资源泄漏。**
8. **G3**：补 `local == 0` 检查（原版有、复刻版漏了）。
9. **G12+N2+N3**：清理文档与默认值的不一致（`applyRoll`、`MFProjection.h:47`）。
10. **§三全表**：按列表接线；其中 `MFEntity.name` 与 `isBox` 是两个"看着有、其实全空"的字段，接线时一起补。
