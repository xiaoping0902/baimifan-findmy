## 当前结论

HUD 基础交互与游戏功能完整度应分别验收。菜单里多数显示设置已经有绘制消费者；交接材料“约 12 个设置项无消费者”的计数已过时。目前明确仅有设置和菜单、没有行为消费者的是**观战模式、直播模式**。

游戏侧更大的缺口是数据来源：真实名称、人物/物资/盒子分类、真实骨骼、人物属性偏移、物资等级价值偏移尚未完成或未校准。现有 UE4 诊断链也没有接入逐帧绘制。能画合成框不能证明真实游戏链闭环。

## 本轮发现的基址与目标生命周期问题

以下是修复前的审查证据，用于说明修复目的；最终状态以本节末的验证记录为准。

1. `Game/MFGameReader.h:78`、`:79`、`:81` 声明 loadBasesFromDefaults、saveBasesToDefaults、calibrationSummary，但对应 .mm 无实现。`HUD/MFHUDAppDelegate.mm:111` 在目标端口取得后调用 load，可能触发未识别 selector。
2. 三个绝对基址没有生产写点或现成 NSUserDefaults 保存键。`App/MFDebugExport.mm:171` 至 `:173` 三同名键只是导出 JSON；`mf.game.libbase` 是另一条 UE4 链的模块基址，不能互相代替。
3. `Game/MFGameReader.h:77` 与 `Features/MFEnvCheck.mm:192` 指引用户去“基址校准”，但 `App/MFProcessViewController.mm:343` 至文件结尾只有目标绑定，没有校准 UI。
4. `HUD/MFHUDAppDelegate.mm:101` 启动时信任落盘 PID，`:102` 的名字仅记日志；未比对进程路径/启动实例，也没有运行中游戏重启后的重新绑定。
5. `App/RootViewController.mm:540` 优先重用落盘 mf.game.libbase，不验证当前 PID/启动实例。ASLR/游戏进程重启后，这类绝对地址不可跨实例复用。

三基址保存/加载的安全约束：使用独立版本化快照，绑定真实目标 task port 对应的 PID、完整精确可执行路径和可取得的进程启动时间；缺身份或身份不匹配时全部清零。无法取得足够身份时宁可保持未校准，不沿用旧地址。读取游戏字段、自动定位白米饭链根对象和校准 UI 属于后续工作。

本轮回归文件为 `tests/game_reader_base_regressions.mm`，直接链接真实 MFGameReader、MFReadBackend、Offsets、MFSettings、MFProjection，以测试自身进程作为目标，不访问游戏内存。先执行修复前版本，确认缺实现造成的真实失败，再实施修复。当前仍待云端 RED 与 GREEN 运行记录，不能写成已经通过。
