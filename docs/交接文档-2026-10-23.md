## 1. 项目目标与边界

复刻一个 iOS 工具 App：

- 伪装成系统「查找」（Bundle ID `com.apple.findmy`），TrollStore 安装
- 主界面控制台：进程选择、清理残留、清理 Key、防封、内核链、诊断导出
- 跨 App 悬浮 HUD：C++ ImGui + Metal，可交互菜单 + 绘制层
- 读取目标游戏内存并绘制 ESP（人物框、物资、背敌提示等）

**明确不做**：授权校验、联网上报、设备指纹采集。

**参考对象**：`白米饭无验证.ipa`（静态逆向结论在所有分析文档里），本项目是**独立重写**。

## 5. 关键发现（按重要性排序）

### 5.1 ★★★ GWorld 静态偏移的十六进制转换是错的（根因级）

**现象**：一键开始 ④ 报「GWorld 不是合法指针」，或整条链第一步就断。

**根因**：mingyun 反编译原文用的是**十进制**：

```c
v8     = Read<unsigned long>(sLibBase + 395003104);   // GWorld
sGName = sLibBase + 389510848;                        // GNames
```

早期分析文档把它们转成十六进制时**两个都算错了**，复刻版照抄：

| 常量 | 十进制原文 | **正确** | 旧值（错） | 差 |
|---|---|---|---|---|
| GWorld | 395003104 | **`0x178B44E0`** | `0x178AA5E0` (=394962400) | 0x9F00 |
| GNames | 389510848 | **`0x173776C0`** | `0x1739D0C0` (=389664960) | 0x25A00 |

**为什么一直没被发现**：偏移量级约 377 MB，两个值看上去都「合理」，任何量级检查都过。

**交叉验证**：用户提供的 Dumper-7 SDK 给出的是**带 image base 的绝对地址**：

```
GWorld = 0x1178B44E0  →  减 0x100000000  =  0x178B44E0   ✓ 与修正一致
GNames = 0x1173776C0  →  0x173776C0                       ✓ 与修正一致
```

**修复位置**：`app/Sources/Game/MFUEOffsets.h` 的 `kMFUE_DefaultGWorld` / `kMFUE_DefaultGNames`，同时保留十进制字面量 `kMFUE_GWorldDecLiteral` / `kMFUE_GNamesDecLiteral` 方便复核。

**顺带**：`MFUEProfile` 的存盘 key 升到 `mf.ue.profile.v2`——旧快照里存着错误值，会被 `loadFromDefaults` 覆盖回默认值。

### 5.2 ★★ 项目里有两条数据链，绘制层原来接错了

| 链 | 起点 | 能否自动建立 |
|---|---|---|
| `MFUEReader` | 模块基址 + GWorld 静态偏移 | **能**，「一键开始」跑的就是它 |
| `MFGameReader` | `rootObjectBase` / `entityArrayBase` / `lootArrayBase` 三个**手工校准**的绝对地址 | 不能，它自己头文件写着「当前尚无基址校准 UI」，全工程没有地方给这三个值赋值 |

绘制层原来接的是 `MFGameReader` → `cameraOK` 恒为 false → **屏幕上永远什么都没有**。

**修复**：`MFDrawingLayer.acquireFrameWithSize:` 改成三级优先：外部数据源 → 已校准链 → UE4 链。

### 5.3 ★★★ task_for_pid 在 A12+/iOS 15+ 上被 PPL 挡死（**这条路已关闭**）

真机「一键开始」分项探测结果（iPad14,4 / 16.1）：

```
✓ 自己(603)         task port = 0x203      ← 假信号！对自己永远成功，不需要任何权限
✗ launchd(1)       kr=0x5 KERN_FAILURE
✗ SpringBoard(32)  kr=0x5
✗ 游戏(601)        kr=0x5
processor_set_tasks 全线 kr=0x4 KERN_INVALID_ARGUMENT
```

环境检测佐证：

```
✓ 沙盒豁免 4/4 可读      ← no-sandbox 生效了，entitlements 机制本身是工作的
· 运行身份 uid=501       ← 不是 root
```

**结论**：
- `no-sandbox` 走 sandbox 层 → 能过
- `task_for_pid-allow` 走 kernel 层 → **被 PPL 挡**（A12+ / iOS 15+ 保护 csblob 里的私有 entitlements）
- **连 launchd 和 SpringBoard 都拿不到**，所以这不是游戏反作弊，是我们 App 的权限根本不被内核认可

**这也解释了白米饭为什么必须配 KFD**：它的「内核端口 → 枚举 task → 端口缓存」走的根本不是 `task_for_pid`。

**错误码对照（重要）**：

| kr | 含义 |
|---|---|
| `0x2` KERN_PROTECTION_FAILURE | 权限不足（entitlement 没生效） |
| `0x4` KERN_INVALID_ARGUMENT | pid 不存在 / 无此 task |
| `0x5` KERN_FAILURE | taskgated 按代码签名拒绝，或目标有 CS_HARD |

### 5.6 ★ 第三条路：Frida（当前主攻方向）

设备是 **Dopamine 真越狱**，跑着 `frida-server`。Frida 用 `ptrace(PT_ATTACHEXC)` 注入 agent 到游戏进程**内部**，agent 读内存 = 读自己地址空间，**完全绕开 task_for_pid / PPL 那套限制**。

架构：

```
游戏进程
  └─ Frida agent（dfm_stream.js）
       读 GWorld → ULevel → Actors → 坐标 / 类名 / bIsPlayerAI
       ↓ UDP 127.0.0.1:25000（本机回环）
复刻版 HUD 进程
  └─ MFExternalFeed → MFDrawingLayer
```

**为什么可行**：Frida 走的是调试器路径，不经过 taskgated 的代码签名检查。

**风险**：ACE 反作弊可能主动检测 ptrace / 可疑 dylib，attach 后可能闪退。**这条需要真机验证，还没试过。**

## 11. 坑与注意事项

1. **不要提交/推送，除非用户明确要求**（本项目的硬规则）
2. **改动前先跑 preflight**，它会抓 framework 声明和 import 路径
3. **`SecTask.h` 是私有头**，用药 `<Security/SecTask.h>` 会报 file not found，要自己 `extern "C"` 声明原型（但链接仍需 Security.framework）
4. **`@property (readonly)` 不自动合成 ivar**，必须在 `@implementation` 的 ivar 块里声明
5. **`HOST_NODENAME` 在 iOS SDK 里可能未声明**，需要 `#ifndef` 兜底（=5）
6. **`mach_vm_remap` 的 `src_task` 必须是 task port**，没有 port 就无法映射——这是白米饭也要靠 KFD 的原因
7. **`task_for_pid(getpid())` 永远成功**，不能作为权限生效的证据
8. **TrollStore ≠ 越狱**：Frida 能力来自 Dopamine 的 frida-server，不是 TrollStore
9. **Dopamine 是半不完美越狱**：iPad 重启后 frida-server 会停，必须重新 Dopamine → Jailbreak
10. **27042 转发会假活**：设备断开后进程仍在监听，要 kill 后重起
11. **构建 run number 会因失败而跳号**，包版本以 `Info.plist` 里的 `MFBuildStamp` 为准，不要按 run number 猜
12. **局域网 IP 是 192.168.2.4**（不是历史文档里的 .6）
