## 已证实的问题与修复

`app/Sources/HUD/MFDrawingLayer.mm` 的正常帧入口先做如下检查：

```objc
if (!self.reader.ready && [MFUEReader shared].libBase == 0) {
    [self noteDrawingActivity:NO];
    return;
}
```

但是，真正的数据源选择位于后面的 `acquireFrameWithSize:camera:entities:loot:source:` 中。该方法会先启动并尝试独立的外部 UDP 接收器，再尝试本地校准链和 UE4 链。上述提前返回使 **没有本地任务端口和模块基址时，外部接收器也无法正常启动或被消费**。这与外部数据源能够独立运行的设计冲突。

修复仅移除这个不适用于全部数据源的提前返回，让各数据源自行检查条件。校准链仍检查 `ready` 和 `rootObjectBase`；UE4 链仍检查 `libBase` 和读取后端闸门；后端仍会拒绝无端口读取。没有启用或修改内核权限补丁。

修复提交：`b05aec3055759a0ff45c9d19b340c1a41c41eca1`。

## 游戏数据链的剩余问题（本轮未修复）

1. 原 `C:/Users/xiaoping/Desktop/Zcode/ios-tools/dfm_stream.js` 使用 `new Socket('udp')`。在当前平板 Frida 17 中，用本项目进程做最小 API 验证，实际返回 `TypeError: not a constructor`。该脚本会在建立定时推流之前退出。证据：`diagnostics/2026-10-24/frida-socket-probe.json`。本轮没有运行或修改游戏推流脚本。
2. 该脚本的 Class/Name 字段和名字池公式与当前项目及用户 SDK 的记录不一致。读取类名失败会变成空字符串，随后实体被过滤；即使收到了空列表的数据包，也不代表取得了可绘制的实体。静态核对依据：用户 SDK 的 `MobileDumper7.log`，以及本项目 `MFUEGNames.mm`。未经本轮游戏运行验证，不能把静态布局直接写成当前场景已确认。
3. `masterEnabled` 和 `drawEnabled` 打开只允许绘制，不会自动运行 Frida 推流脚本，也不会自动获得目标任务端口。SDK 和离线 IPA 提供结构与代码，不能代替运行时数据源。
4. `task_for_pid` 失败只证明该次端口请求失败。旧文档中“PPL 永久关闭所有路径”“必须启动内核且是唯一出路”等归因缺少本轮证据。KFD 初始化、目标进程读取权限、游戏数据解析、投影和 Metal 上屏是不同环节，不能用其中一个状态替代其他环节。

因此，本轮交付是 **绘制入口修复及经过合成数据验证的包**；真实游戏人物、骨骼、物资等效果仍须等游戏场景可用后单独验收。

## 之后可独立完成的渲染自检

1. 如果旧悬浮窗仍在运行，先在原控制台点击“结束悬浮窗”。
2. 使用已有 TrollStore 打开 `dist/drawing-fix-M5.91/FindMy-M5.91-DrawingFix.ipa` 覆盖安装。
3. 在控制台确认 `M5.91 / b05aec3-r91`，然后点击“启动悬浮窗”。
4. 在悬浮菜单开启“总开关”“启用绘制”，在设置中打开“渲染自检”。该自检使用合成图形，无需游戏前台或启动内核读取。
5. 检查结束后关闭“渲染自检”。物理可见性以用户看到的平板屏幕为准，截图/录屏空白不能单独否定安全画布中的显示。
