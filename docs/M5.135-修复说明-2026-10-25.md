# M5.135 修复说明（2026-10-25）

> 这一版只做一件事：**把"读得到"变成"读得对"**。
> 内核链路本身没动，动的是偏移、相机、以及多线程共用一套内核句柄的问题。

---

## 1. 三组偏移（这是"画不出来"的根因）

全部用 MobileDumper-7 SDK（游戏 1.201.37117）逐字段核对，不是猜的。

| 位置 | 旧值 | 新值 | 为什么旧值是错的 |
|---|---|---|---|
| `ULevel::Actors.Data` | `0x1F0` | **`0x98`** | 0x1F0 落在 `Pad_1E5[0x5B]`（0x1E5..0x240）填充区，读到的是被清零的填充字节 |
| `ULevel::Actors.Num` | `0x1F8` | **`0xA0`** | 同上 |
| Actor 坐标 | `AActor+0x220` | **`AActor+0x180` → `+0x220`** | 少跳了 RootComponent：`+0x220` 是 **ComponentToWorld.Translation**，不是 AActor 字段 |
| 相机 POV | 扫出来的 `cam_cache` | **`CameraManager+0x2D60+0x10`** | 偏移本来就能查；扫描判据太松还会永久存盘 |
| POV 内部 | Rotation `0x0C` / FOV `0x18` | **`0x10` / `0x1C`** | 这个 build 的 Location 是 16 字节 `FEncVector`，不是 12 字节 `FVector` |

坐标这一行值得单独说：`0x220` 本身**没错**，错的是"从谁身上读"。
`USceneComponent::K2_GetComponentLocation` 的 native 实现是
`GetComponentTransform()`（存根就两条：`add x0,x0,#0x210; ret`）再读 `+0x10` 的
Translation —— 所以 `ComponentToWorld` 在 `0x210`，Translation 在 **`0x220`**。
旧代码把这个偏移套在 `AActor` 上，正好落进 `Pad_1FA[0x76]` 的填充区，恒为 0。

**为什么之前看起来"像偏移失效"**：填充区不会报错、不会崩，只是恒为 0。
于是日志写成「Actors.Data 非法 / 数量异常」，把人往"版本更新导致偏移失效"的方向带。

### 顺带纠正两处命名（值是对的，名字是错的）

- `0x10C0` 不是 `PlayerState`，是 `AGPCharacterBase::TeamComp`（`UGPTeamComponent*`）；
  下一跳 `+0x108` 才是 `UGPTeamComponent::TeamID`。两跳算下来正好命中，队伍功能一直没问题。
- `0x3A0` 是 `AController::Pawn`（合法字段）；`AcknowledgedPawn` 在 `0x3F0`，两个都在。

## 2. `FEncVector` 到底加不加密：不加密（已用二进制证死）

SDK 里每个 UFUNCTION 都带 `NativeExecOffset`，据此在 378.8 MB 的 Mach-O（从脱壳 IPA 里取出）定位到：

```
DecVector  @ 0x109DFA15C   →  实际取值在 0x109880BA8：
    ldr   q0, [x0]
    mov   s1, v0.s[1]
    mov   s2, v0.s[2]
    ret
```

就是原样返回 X/Y/Z。`EncVector`（`0x10FCC599C`）同样只做 12 字节拷贝。
`EncHandler` 唯一被用到的地方是末尾 `ldrb [sp,#0xF] / tbnz bit0` 的分支，只通知动态句柄，**不参与数值变换**。

**结论**：`+0x168` 头 12 字节直接当三个 float 用；不需要解密，也不需要判 handler。
`mf-live.txt` 里的 `encrypted` 计数从此只作参考。

## 3. 内核读取改成串行

`MFKernelBridge.h` 一直写着"禁止并发调用 kread/kwrite"，但 M5.124 之后 HUD 里同时有：

- 持续读取：3 秒一拍，global queue
- 绘制：60Hz，`_drawableQueue`

而失败落点是**每进程一份**的 `g_fail_jmp` / `g_fail_armed` —— 两个线程同时进来，
要么 `longjmp` 跳到别人的栈帧（崩溃），要么一方清掉 `g_fail_armed` 让另一方直接 `abort()`。

改法（M5.135）：

- `MFKernelBridge.m` 加一把**递归** pthread 锁；
- `mf_kopen / mf_kclose / mf_kread / mf_kwrite / mf_kread32 / mf_kread64 / mf_kwrite32 / mf_kwrite64 / mf_pid_chain`
  变成 `*_locked` 内部实现 + 公开包装（加锁范围覆盖 setjmp 区域）；
- `MFPageTable.m` 的 `mfpt_translate / mfpt_read / mfpt_probe32 / mfpt_lowest_mapped_page`
  也整套加锁 —— 一次遍历的 3 次 kread 必须原子，否则 v2p 缓存会读到半更新条目；
- 顺带解决「退出时 `mf_kclose` 与在途读并发」的老问题：kclose 会等当前读完成。

## 4. HUD 侧的日志与线程修正

| 问题 | 修法 |
|---|---|
| 无论链是否读通都写 `RESULT OK` | 改成按 `level/actors/num/valid` 分支，读不到写 `RESULT PARTIAL` |
| `valid` 不能代表坐标可信 | 日志里明确标注；NaN/Inf 单独计数并剔除 |
| `encrypted` 把 `Index` 当加密标志 | 按 `FEncHandler` 拆开：`idx = h & 0xFFFF`、`enc = (h >> 16) & 0xFF`，且读失败不再算"未加密" |
| 1 秒定时器会把 `libBase`/`modeFlag` 清零 | `kernelViaKFD` 提前到 attach 成功那一刻置位，老绑定立刻停 |
| 从后台线程往 `mainRunLoop` 塞 NSTimer | 统一回主线程创建 |
| 3 秒一拍但一轮可能超过 3 秒 | `tryLock` 闸门，上一轮没跑完就丢掉这一拍 |
| `failStartup` 走 `_exit()`，跳过 atexit | 退出前显式 `mf_kclose()` |

## 5. 两个内核入口互斥（跨进程哨兵）

主 App 和 HUD 是两个进程，各自的 `mf_is_open()` 只看自己 —— 谁后 `kopen` 谁撞
`perf.dev.fd > 0`，而按报告 §8.2 那个状态只能重启设备。

`MFKernelBridge.m` 里加了一个共享文件上的 `flock`：

```
/var/mobile/Media/mf-debug/kernel.owner
```

- `kopen` 前 `LOCK_EX | LOCK_NB`，拿不到就 **返回 -4，一个字节都不碰内核**；
- 拿到后把本进程 pid 写进去（错误信息里能看出是谁占着）；
- `kclose` / 进程退出（fd 关闭）自动释放；
- 文件开不了（沙盒/权限）时降级放行，不让诊断设施挡住主线。

`MFKernel.mm` 里对 `rc == -4` 特判：**不置 `gMFKernelPoisoned`** —— 因为内核没被动过，
用户关掉悬浮窗之后可以直接重试，不用重启 App。

> 局限：它只能防"同时开"。上一个进程被硬杀、perfmon 还脏的情况，哨兵看不出来，
> 仍然只能重启设备。

## 6. 游戏重启后的重连看门狗

`root` 以前是 `startLiveReadTimerWithRoot:` 按值捕获的，游戏一重启就永久失效
（每 3 秒稳定打 `rc=-11`，永远不重连）。

现在：

- `liveRoot / livePid / liveFailStreak` 提到实例属性；
- 每拍读不到 GWorld 就累加，**连续 2 拍**触发一次检查；
- 重新枚举进程：
  - 找不到游戏 → 记一行，继续等；
  - pid 没变 → 只清计数（多半是关卡还在加载，不折腾）；
  - pid 变了 → **先在不动共享后端的前提下**用 `mf_pid_chain` 取新 pmap 根表、
    找模块基址、校验 `0xfeedfacf`，全部通过后才 `attachKFDPid` 并更新
    `livePid / liveRoot / MFUEReader.libBase`。

顺序很重要：反过来会留下「后端指向新进程、libBase 还是旧的」的半吊子状态。

## 7. 宽松读 + 缓存 TTL

### 7.1 `mfpt_read` 不再"一页失败全批作废"

旧实现里 `mfpt_read` 只要碰到一页没映射就 `return`，前面读到的字节全丢。
读一个 600 项的 Actor 指针数组（4.8 KB，必然跨页）时，一处空洞就整批归零，
表现成"扫描结果 0 个"。

现在拆成三层：

| 函数 | 语义 |
|---|---|
| `mfpt_read_inner` | 逐页读，失败就停，用 `got` 回报已读长度 |
| `mfpt_read` | 严格版：`got != n` 仍算失败（老语义不变） |
| `mfpt_read_partial` | 宽松版：返回实际长度，由调用方决定能用多少 |

后端加了 `-readRemotePartial:into:size:`；`MFUEReader` 与 `MFDrawingLayer` 读
指针数组时改用它，并且 **`calloc` 先清零** —— 没读到的槽保持 0，
`MFUEIsValidPtr(0)` 自然跳过。

### 7.2 v2p 缓存加 TTL

旧缓存只要 `root` 不变就永久有效。游戏会释放/重映射页面（关卡切换、对象销毁），
旧条目仍把 VA 翻到那块物理页**现在的住户**上 —— 读到别人的数据，幽灵框，还不报错。

现在每条缓存带时间戳，**超过 3 秒按未命中**重新走页表；root 变化仍然整表作废。
`clock_gettime(CLOCK_MONOTONIC)` 不可用时退化为"永不过期"（stamp=0 视为空槽，
实际等于禁用缓存），不会因为时钟问题读错数据。

## 8. 还没做（剩下的）

1. **主 App「启动内核」入口的收尾**：哨兵已经让它安全失败，但按钮本身还在；
   下一步要么删掉，要么并进「诊断」页。
2. **字段级节流**：绘制每帧读相机、轮转读坐标；位置 100ms / 名字 300ms 的
   分级节流还没做（参考同类产品的做法）。
3. **`ComponentToWorld` 的更新时机**：理论上引擎可能晚一帧（`bComponentToWorldUpdated`），
   真机上要看框有没有滞后；如果明显，再考虑用 `LastUpdateLocation` 之类做平滑。
4. **真机验证**（下面一节）。

> 首页引导文案已同步改成新顺序（先悬浮窗、后游戏；主 App「启动内核」标成诊断用），
> 不再是「开游戏 → 点启动内核 → …」那套会撞哨兵的旧流程。

## 9. 真机验证顺序

1. 装新版，按「启动悬浮窗 → 开游戏」跑一遍。
2. 看 `/mf-debug/mf-hud-kfd.txt`：
   - 应该是 `RESULT OK`（level 非 0、num 几百量级、valid > 0）；
   - 如果是 `RESULT PARTIAL`，看 `[chain]` 行哪一步是 0。
3. 看 `/mf-debug/mf-live.txt`：
   - `world/level/actors` 三行都非 0；
   - `A[i] ... pos=` 的数值稳定、量级合理（几千米以内）；
   - `scan: valid=… encrypted=… nonFinite=…`：`nonFinite` 应为 0。
4. 看画面：框应该出现在人身上，而不是满天飞或全空。
5. 退出请用悬浮窗菜单的「退出」—— 现在会先 `kclose` 再结束进程。
